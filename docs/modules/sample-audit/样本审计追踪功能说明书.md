# 样本审计追踪功能说明书

本方案覆盖两类修改：样本相关业务表的修改，以及用户、角色、授权和配置等非样本修改。两类共用事件与逐记录前后值；查询分为“变更记录”和“样本履历”。subbarcode 在不同药企之间也全局唯一；同一样本可有多份数据，以 analysis_id + subbarcode 区分分析数据批次。暂按 file-v1 → report-v1、file-v2 → report-v2 关联，在一个样本的时间线上汇总导入、修改、质控、位点上传与报出、状态流转、解读、生成和交付记录。

本期仅设计留痕与查询。所有 audit 表、字段、接口和页面增量均为拟议方案，尚未实现；本文件不表示系统已经符合 GxP。既有业务中的报告审核、签署、退回等动作继续作为被记录的业务事件，不新增审计复核或数据还原功能。

## 1 目标与边界

### 1.1 已确认目标

AUD-01：查询一个样本在系统内发生过的录入、质控、数据处理、解读、报告生成及交付过程。

AUD-02：记录样本相关业务表与非样本对象的新增、修改、删除，保存操作者、操作时间、来源、结果及字段前后值，覆盖多表、多行、批量、接口与后台处理。非样本对象至少包括用户、角色及授权关系，后续新增对象按同一规则接入。

AUD-03：样本编号唯一，且跨药企全局唯一。同一样本多次上传可对应多份数据，以 analysis_id + subbarcode 定位批次；暂定一份数据版本对应一份报告业务版本。保留原有对象的真实主键，区分数据版本、报告业务版本与同一报告的文件生成次数。

AUD-04：明确数据怎么存、各模块如何持续接入、如何查询以及在哪里展示；提供可供后续开发使用的规则和验收用例。

### 1.2 本期范围

包括两类对象的自动留痕、变更记录查询、唯一样本检索、按操作时间组合的样本流转解读履历、字段变更详情、数据与报告版本及发送尝试查询、访问隔离和存量基线。样本过程记录既包括字段修改，也包括确实发生的导入、上传、状态迁移及解读动作；仅靠字段差异不能覆盖全部过程。查询已存在的历史制品属于本期设计；不承诺历史任意时点的业务还原。

不实现审计复核、审计签批、历史一键还原、任意历史版本恢复、样本合并治理、通用流程引擎或完整事件溯源重构。后续通过稳定 event_id 和 schema_version 关联扩展数据即可，本期不创建空接口、占位表或不可用按钮。

### 1.3 阅读方式

第2章是代码事实；第3至7章是建议设计；第8章是开发接入计划；第9章是未执行的验收用例；第10章列出实施前须确认的事项。样本编号跨药企全局唯一是已确认业务前提。当前仓库 DDL 只有 tenant_id 与 subbarcode 联合唯一，尚未从数据库层保证跨药企唯一；实施时须补充全局唯一校验与最终数据库约束，规则冲突按本次业务确认处理。本文不执行迁移，也不将不同药企同号视为正常业务。

### 2.2 对设计的直接影响

不能复用流转页“只取最新”的关联来构造完整历史。不能把 analysis_id、report_id、变异 id 或文件路径当成同一种样本身份。不能仅保存请求参数，因为默认值、合并更新、计算结果、XML 更新与事务回滚都会使请求与实际落库结果不同。

history_somatic、history_germline、report_variant_history 和邮件发送日志各有业务用途，应继续保留；它们会发生更新或复用，不能替代独立审计。新增审计只记录事实，不改变已有业务审核规则。

当前 analysis_data 的唯一键包含 tenant_id、subbarcode、product、analysis_date；data_file_status 以 file_id 为主键并带 analysis_id 和 subbarcode。相同产品、相同日期再次上传是否新建分析，不能仅由现有唯一键推断。新业务版本须能区分独立数据批次；若外部写入方会复用 analysis_id 并覆盖文件，应在实施阶段调整版本接入规则或保存不可变输入清单，不能仅靠文件名或当前路径识别旧数据。现有 enter 在报告完成后可为同一 analysis_id 创建新 report_id，是代码事实；暂定的数据版本与报告版本对应关系属于本次需求，二者应在实施前对齐，审计不得篡改已有一对多历史。

## 3 样本编号与关联设计

### 3.1 唯一业务标识与真实主键

样本编号 subbarcode 是已确认的全局唯一业务标识，不同药企不会拥有相同编号的不同样本。用户输入编号即可打开一个样本的履历，不设置同号多实例选择流程。现有 sample_file.id 作为录单对象的稳定内部关联，不再新增追踪根表、历史别名表或业务表 sample_id 列。

样本编号唯一不代表下游记录一对一。analysis_data 仍按 analysis_id 区分分析，analysis_report 按 report_id 区分报告，质控、文件、位点及子表各按真实主键记录。一个样本的这些对象均可汇总到同一履历。

### 3.2 关联与授权

业务服务在授权范围内按 subbarcode 查唯一录单样本，冻结 sample_file.id、编号和药企归属。已有 analysis_id、report_id 的入口须交叉核对其编号与父子关联；不能把 analysis_id 或 report_id 当作样本主键。认证与租户授权仍由服务端执行，编号唯一不代表任何用户都能查看该样本。

外部数据可能先于录单到达：事件与样本关联先保存唯一 subbarcode，sample_id 暂空；录单到达后仍按该编号检索早期事件，不修改已经保存的审计证据。若未来明确允许编号更正，则通过同一 sample_file.id 和更正事件关联旧号；不能自行推断编号永远不可修改。

查询若发现违反唯一性约束的多条录单记录，返回数据完整性错误并阻止错误关联，不设计成让用户选择其中一条的正常流程。药企归属应来自授权上下文和唯一录单记录，不根据客户名称随意切换租户。

### 3.3 生命周期规则

| 情况 | 身份与记录规则 |
| --- | --- |
| 同一编号再次导入 | 定位同一样本；实际有变化则 UPDATE，无变化记 NO_CHANGE |
| 原业务允许编号由 A 更正为 B | sample_file.id 不变；更正事件保存旧新号；下游引用同步一致后提交 |
| 原导入逻辑恢复已软删样本 | 原 id 和编号不变；记录 RESTORE 与真实字段变化 |
| 样本软删除 | 审计快照继续可查；不把已删样本编号重新分配给另一份样本作为本期新语义 |
| 质控旧行清除后重建 | 保存旧质控主键及删除前快照，再保存新质控主键；都关联同一样本 |
| 一个样本多产品、多分析批次 | 按 analysis_id 分支，保留产品和日期快照 |
| 外部数据先到、录单后到 | 先按唯一编号保存审计；后续查询自动包含录单前事件 |

本期不新增改号、编号复用或样本合并功能。若现有业务实际发生编号更正，应审计该动作，并在 audit_event_subject.context_json 保存 oldSubbarcode、newSubbarcode 与 sampleId；旧号入口和录单前事件的关联由这些事实解析，不另建别名表。不能借审计模块改变已有样本生命周期。

### 3.4 关系与时间

样本层用 subbarcode 汇总全部历史；数据层用 analysis_id + subbarcode 定位一次分析数据批次；报告层用 report_id 定位基于该数据批次形成的报告；文件生成层用 report_id + generation_no 定位同一报告的一次渲染。data_file_status.file_id 区分批次内各个真实文件，一次数据上传可能包含多个文件，不把单个文件主键等同于分析批次。

暂定业务链为 S001 → 数据v1（A10及其输入文件）→ 报告v1（R30），再次上传形成数据v2（A20及其输入文件）→ 报告v2（R40）。v1／v2 是已登记的数据与报告业务版本标签，不能用列表行号、文件名后缀或最新更新时间临时推导。建议冻结在 subject.context_json 的 dataVersionLabel、reportVersionLabel、sourceFileIds、inputManifestSha256 中；具体版本分配以实施时的数据接入契约为准。生成事件与 dependencies_json 同时保存实际输入清单和内容校验值。

同一报告因渲染失败重试或重新生成得到 generation_no=1、2，仍归属于原数据版本和报告业务版本；不会自动成为新的 report-v2。重新解析同一数据也不自动代表新数据版本。若原业务确实在同批数据下建立了另一报告，保留真实 report_id 分支并注明对应关系，不强行删除或合并历史。一项事件可以影响多个样本，通过事件与样本关联表表达。

样本履历默认按 occurred_at 升序展示，即本系统确认的操作／变更发生时间；同一毫秒按 event_id 升序稳定排序，也可切换倒序。导入、上传、无字段变化的已处理动作、状态迁移和解读均保存自己的事件时间，不能事后对各表当前 update_time 做 UNION 来冒充完整历史，因为后续修改会覆盖旧时间。

recorded_at 保存审计登记时间，用于追查延迟；source_occurred_at 保存外部声明时间并显示来源。失败或请求中事件使用该次尝试的发生时间；导入旧数据使用基线登记时间，旧业务时间仅作为来源信息，不伪造实时审计。服务端统一校时；延迟到达事件可以插入其发生时间位置，并提示登记延迟。同一事务的多表改动作为一个事件展开；一个报告的多步动作仍分别留痕。时间线是线性展示的事实序列，允许重传、失败、退回和重做；时间排序不证明并发事务的全局提交先后，因果关系仍按 parent_event_id 和真实状态转换判断。

### 3.5 两类修改与两个查询视图

样本相关修改包括样本信息、湿／干质控、数据和位点文件、是否报出及报出集合、报告状态迁移与解读内容。每项事件关联唯一编号，可进一步关联 analysis_id、file_id 和 report_id。样本信息等公共阶段没有 analysis_id 时不强行挂到某个数据版本；查看单个分析批次时，允许显式包含“样本公共事件”，并标明其范围，不复制生成多条历史。

非样本修改包括用户、角色、用户角色绑定、角色菜单授权及产品／规则／模板等配置对象。它们保存真实对象主键和前后值，不填虚构 subbarcode，不给全部样本逐一追加配置修改事件。样本实际使用的配置或模板版本，记录在该次分析／解读事件及报告输入快照中。操作者的昵称或角色事后变化，不回写旧事件的操作者快照。

“变更记录”查询两类对象的增删改，可按范围、模块、对象类型／主键、操作人、动作和时间筛选；“样本履历”按 subbarcode 查询该样本的所有过程事件及关联字段变化。二者读取同一份审计事实，避免重复写两套日志；没有行变化的过程事件可有零条 change，但仍保留动作、结果和上下文。

## 4 数据存储设计

### 4.1 四张建议表

| 拟议表 | 保存内容 | 解决的问题 |
| --- | --- | --- |
| audit_event | 一次业务动作的标题、主体、来源、结果及关联号 | 聚合一次操作，识别任务、批量及外部结果 |
| audit_event_subject | 事件与受影响样本的关系和当时上下文 | 多样本事件与按样本索引查询 |
| audit_change | 每张表每条实际记录的新增、修改、删除前后值 | 多表、多行、重建、复杂 JSON 的证据 |
| audit_report_artifact | 每次生成及签署产物的不可变文件元数据 | 多版本报告与实际交付版本追踪 |

### 4.2 公共约束

以下是建议物理字段，不是已经存在的数据库结构。四表均采用 id bigint AUTO_INCREMENT 主键；tenant_id varchar(20) NOT NULL DEFAULT '000000'，应用仍须显式校验业务归属，不能把默认值当归属解析兜底。均设置 idx_tenant_id，以 InnoDB、utf8mb4、utf8mb4_general_ci 建表；四张 audit 表的业务唯一索引以 tenant_id 开头。样本业务表的全局编号唯一属于本次已确认的业务例外，应在实现阶段为 sample_file.subbarcode 制定单独全局约束并同步更新数据库规则及闸门例外；本次不修改该规范或 DDL。

四表保留 create_by bigint NULL、create_time datetime NULL、update_by bigint NULL、update_time datetime NULL，不添加 create_dept 或 del_flag。证据表只 INSERT 和 SELECT；update 列首次写入后不再变更，不使用自动更新填充破坏证据。业务表保留自身原有软删规则。

数据库关联采用应用校验，不设置指向可删除业务表的级联删除。父子审计记录必须属于同一租户；查询与写入均检查，跨租户批量拆成各租户事件。大整数通过 JSON 字符串传输，避免前端 number 精度损失。

业务时间字段建议 datetime(3)，按 UTC 写入并明确展示时区。只有启停语义才使用 active／inactive；本方案的动作与结果枚举不属于启停状态。

### 4.3 样本关联列

审计中的 sample_id 是已有 sample_file.id 的快照，subbarcode_snapshot 是当时的唯一样本编号。无需新增业务主键或给五张业务表增加关联列。业务行已删除时仍可通过审计关联列和编号快照查询，不设置业务删除到审计的级联删除。

外部先到的数据允许 sample_id 暂空，但 subbarcode_snapshot 必须有值。样本专属变更明细同样保存编号快照；共享配置对象的 sample_id 和编号可空，其可见范围按共享对象权限判定。编号更正是否允许仍遵循原业务，不能由“唯一”推导出“不可更正”。

### 4.4 业务事件

| 字段 | 建议类型及可空性 | 含义与约束 |
| --- | --- | --- |
| event_key | varchar(160) 非空 | 服务端生成的审计幂等键；同一已提交操作的重放复用它 |
| operation_id | char(32) 非空 | 一次用户／系统业务意图，跨阶段结果共享此值 |
| audit_scope | varchar(16) 非空 | SAMPLE／NON_SAMPLE；区分样本相关与非样本对象 |
| batch_id | char(32) 可空 | 一次导入或任务批次，多个独立事务共享 |
| parent_event_id | bigint 可空 | 请求、回调、重试等明确因果关系 |
| stage | varchar(32) 非空 | SAMPLE／WET_QC／BIO_QC／ANALYSIS／INTERPRETATION／REPORT／DELIVERY／SYSTEM |
| event_code | varchar(64) 非空 | 稳定动作代码，中文文案另存快照 |
| title | varchar(300) 非空 | 可读摘要，不拼接其他样本敏感内容 |
| outcome | varchar(24) 非空 | STARTED／SUCCESS／FAILED／NO_CHANGE／UNKNOWN／SUPERSEDED |
| occurred_at | datetime(3) 非空 | 服务端确认的动作发生时间 |
| recorded_at | datetime(3) 非空 | 服务端写入审计的时间 |
| source_occurred_at | datetime(3) 可空 | 上游声明的时间，须标明来源 |
| actor_type | varchar(24) 非空 | USER／SERVICE／JOB／CALLBACK／MIGRATION |
| actor_id | varchar(100) 非空 | 用户或服务主体稳定标识，服务端确定 |
| actor_name | varchar(120) 非空 | 当时显示名称快照，不随改名变化 |
| actor_tenant_id | varchar(20) 可空 | 操作主体归属，区别于业务 tenant_id |
| source_system | varchar(64) 非空 | 已认可来源系统 |
| request_id | varchar(100) 可空 | 请求追踪号，不等同于幂等键 |
| source_event_key | varchar(160) 可空 | 上游事件／消息号，可辅助去重 |
| reason | text 可空 | 原业务已有原因或更正说明；自动任务使用结构化来源说明 |
| context_json | json 可空 | 状态转换路径、任务参数摘要、原系统定位、来源证据引用 |
| schema_version | smallint 非空，初值1 | 事件及快照解释版本 |

唯一索引 uk_audit_event_key(tenant_id, event_key)；查询索引 idx_event_operation(tenant_id, operation_id, id)、idx_event_batch(tenant_id, batch_id, id)、idx_event_stage_time(tenant_id, stage, occurred_at, id)、idx_event_scope_time(tenant_id, audit_scope, occurred_at, id)。原始上游 key 应结合来源和业务范围构造 event_key，不直接信任客户端任意填值。

audit_scope=SAMPLE 的成功写入事件必须有样本 subject；NON_SAMPLE 不建 subject，stage 使用 SYSTEM 或实际配置阶段。非样本事件保存自身所属租户或平台范围，并由独立权限控制；不得用操作者当前选择的样本或药企兜底。

开始、成功、失败是不同的只追加事件，不更新同一事件的 outcome。审计写入与业务幂等要一起实现：不能业务重复执行后仅把第二条日志去掉。用户有意发起的再次生成／再次发送产生新的 operation_id；网络重试同一意图才复用幂等键。

### 4.5 事件与样本关联

| 字段 | 建议类型及可空性 | 含义与约束 |
| --- | --- | --- |
| event_id | bigint 非空 | 父事件 |
| sample_id | bigint 可空 | 当时 sample_file.id；录单前事件可空 |
| subbarcode_snapshot | varchar(160) 非空 | 事件发生时的唯一样本编号 |
| analysis_id | bigint 可空 | 本事件针对的分析批次；事件跨多个批次时见 context_json |
| report_id | bigint 可空 | 本事件针对的报告；事件跨多报告时见 context_json |

唯一索引 uk_audit_event_subject(tenant_id, event_id, subbarcode_snapshot)。增加 idx_subject_number(tenant_id, subbarcode_snapshot, event_id)；查询索引 idx_subject_timeline(tenant_id, sample_id, event_id)、idx_subject_analysis(tenant_id, analysis_id, event_id)、idx_subject_report(tenant_id, report_id, event_id)。

样本时间线查询由 subject 按编号定位 event，再按 event.occurred_at、event.id 组合排序；现有编号与事件索引用于关联过滤，不能仅按 subject.id 代替操作时间。实施时基于真实数据量用执行计划检验索引与分页性能，不预先增加未经验证的冗余排序列。

同一事件对同一样本只建一条关联，不按明细行复制时间线。多批次／多报告动作应优先拆成语义明确的子事件；必须同事务的整体动作在 context_json 的 analysisIds、reportIds 字符串数组列出全部范围。过滤同时检查单值列与 JSON 数组精确成员，不使用 LIKE 或只查一个任意 report_id；单样本页面仍只显示一张事件卡片。

| 字段 | 建议类型及可空性 | 含义与约束 |

before／after 是纳入审计字段集合的完整业务快照，不是任意 ORM 实体的全量序列化。字段集合由模块接入规则明确定义，涵盖影响业务含义的字段；自动更新时间等技术列默认不进入差异，但事件本身必须记录操作时间。密码、密码哈希、Token、密钥与认证会话内容不得进入 before／after、差异或 context；密码重置只记录对象、执行者、动作和结果。手机号等个人信息按字段规则受控保存和展示。大文件记录摘要与制品引用，不把文件正文塞进每行 JSON。新增、删除即使所有值为空，也必须有对象级动作。实现时对单行快照、事务明细总量和数据库报文设置限额；超限应在提交前明确拒绝或采用受控的不可变外置快照，不能截断内容后标记为完整。

### 4.8 建表与迁移边界

本期交付设计字典，不提供或执行最终 DDL。进入实现前先核对运行库版本、样本编号唯一约束及外部写入方，再生成独立的四张 audit 表建表脚本。迁移脚本须走数据库规范闸门和隔离库验证，不修改已发布历史迁移。

现有业务表主键和关联保持原有结构。本方案不新增 sample_id 到业务表；只在审计表保存已有主键与编号快照。存量导入时，能够定位录单记录则填 sample_id；只有唯一编号而尚无录单记录则标明关联缺口，后续按编号汇总。

## 5 新增修改删除如何持续留痕

### 5.1 写入位置与依赖

建议新增独立 ruoyi-audit 模块，提供一个具体 AuditRecorder 写入组件和审计查询服务。报告、质控、系统用户与角色等纳入范围的模块依赖它；审计模块只依赖公共基础能力，不反向依赖报告／质控服务。样本模块自行解析编号与批次并传入；用户／角色模块传真实对象和非样本范围，不依赖样本模块，避免循环依赖。

统一组件负责校验上下文、保存事件／样本关联／明细以及受控差异处理。业务服务负责确定业务动作、读取旧数据、执行更新、读取结果、解释字段和确定受影响样本。不能用通用 AOP 猜业务关联，也不能向前端暴露通用“写入审计”接口。

新增一个需要审计的写操作时，开发者依次完成：识别事务入口；登记对象和字段口径；判定样本或非样本范围，样本事件解析唯一编号、批次和现有主键，非样本事件解析对象主键；捕获旧值；执行业务并读取实际结果；共同写入事件及明细；补充正常、并发、回滚、重试和权限用例。接入映射随模块代码维护，不增加可被普通管理员关闭关键审计的开关。

### 5.2 事务与真实值

本地数据库写操作在同一 Spring 事务内完成。先锁定目标行或使用条件更新／版本检查，保存实际旧值，再执行业务，读取最终新值，最后插入事件、subject 与 change。审计插入失败应让该事务整体回滚。

涉及新增对象先获取真实自增主键再写审计；多表动作只在最外层业务边界生成一个事件，各协作步骤贡献明细，避免每个 Mapper 重复生成看似独立的动作。插入 subject、artifact 的内部顺序由统一写入组件控制并共同提交；应用校验须处理同事务中新建的父子关系。

不能依赖同一 Bean 内部调用带 @Transactional 的私有／普通方法来建立新事务。现有未完整包事务的生成、发送、逐行导入等入口，需按实际提交边界重整为可代理调用或显式事务模板。

失败事务不留下 SUCCESS 事件。拒绝、失败尝试需要保留时，在原事务已回滚后另写 FAILED 事件，不伪造 before／after 已变更；独立失败日志也写入失败时应报警，不能谎称已完整留痕。

### 5.3 差异口径

| 动作 | 留痕规则 |
| --- | --- |
| 新增 | CREATE；before 为 SQL NULL，after 为实际落库快照与真实主键 |
| 修改 | UPDATE；比较实际持久化前后值，只列真实变化字段 |
| 软删除 | SOFT_DELETE；保留前后快照及 del_flag 变化，不隐藏旧记录 |
| 物理删除 | DELETE；删除前保存快照，after 为 SQL NULL；级联逐行纳入同事件 |
| 删除后重建／整批替换 | 同事件保存 DELETE／SOFT_DELETE 与 CREATE 明细；真实新旧主键分别保留 |
| 既有业务恢复软删行 | RESTORE 加字段差异；这是被审计业务动作，不是审计提供还原能力 |
| 值未变化 | 明确用户或接口处理记 NO_CHANGE，不造 UPDATE；普通读取不刷时间线 |

未传字段与显式清空必须区分。PATCH／合并更新以最终数据库值为准；SQL NULL、空字符串、数字0、字符串“0”和空数组不能混同。decimal 依据业务精度比较，字符串不擅自 trim 或改大小写。JSON 对象按键语义比较；无序集合按已确认业务键比较，有序列表保留顺序。

新旧子记录不按数组下标配对。保留主键时按主键比较；换了主键则记录删除／新增，并可在 context_json 给出业务替换说明。一次更新命中多行时捕获所有真实主键，校验数量，不因某业务字段“看起来唯一”而只留一条。

### 5.4 批量与跨表

一次原子事务修改多个样本时，保存一个事件、多条 subject、多个 change；非样本的多表修改保存一个 NON_SAMPLE 事件和多个 change，不创建 subject；每个 change 标记所属样本或共享范围。页面按样本裁剪明细，不泄露同一事件中其他样本数据。

Excel 等允许逐行部分成功的任务使用 batch_id 聚合，逐行或约定分块事务独立记录；不能先提交所有业务后在循环外补一次日志。若现有接口是整批事务，应保持整批共同回滚语义；只有明确变更接口约定后才改为分块提交。跨药企批次按药企分事件，批次汇总也只能返回授权范围。

报告提交审核可能同时更新 analysis_report、history_somatic／history_germline、report_variant_history 及复用日志，统一作为一个“报告提交”事件保存。驳回重提时，现有检出历史的 upsert 前后值也必须进入审计。

共享 history 行的修改要记录真实 history 主键及本次操作样本的使用上下文，不把该行的当前值显示成所有旧样本当时的解读结论。产品、规则、模板变更作为配置对象事件单独留痕；某样本实际采用的版本在处理事件／报告输入快照中冻结，不向所有历史样本追加“发生过配置修改”的伪事件。

用户新增并分配角色时，保存一个“创建用户”事件，内含 sys_user 新增及 sys_user_role 新增明细；角色修改并替换菜单权限时，保存一个“修改角色权限”事件，内含 sys_role 前后值及 sys_role_menu 成员删除／新增。授权、撤权和账号启停有各自事件；对象关联表使用真实复合主键，记录实际已提交的成员变化，不能只保存表单中的 roleIds 或 menuIds。

### 5.5 报告生成签署与交付

生成采用短事务登记意图并冻结本次输入，再在事务外渲染文件，最后短事务登记制品与结果。并发期间记录版本已变化时，保存“生成结果已过期，未应用”的 SUPERSEDED 事件，不能把旧输入产物覆盖成当前报告。文件校验与永久存储成功后才登记可查询产物；失败记录失败阶段，不把半成品标成正式版本。

报告文件本身继续使用不覆盖的路径，并纳入保留管理。历史页面只能通过 artifact id 鉴权下载；若旧文件已缺失，显示“元数据存在，文件不可用”，不能拿当前文件替代。input_snapshot_ref 指向当次实际输入，dependencies_json 不仅保存会被覆盖的模板／规则 id，还保存内容摘要或受保留的具体快照。

外部邮件或签名不能通过数据库回滚撤销。先持久化 REQUESTED／STARTED 事件，再调用服务，随后追加 SUCCESS／FAILED／UNKNOWN 事件；超时无法判断是否已送达时记 UNKNOWN，后续查证再追加结果。每次有意重试用新的尝试号，与原事件建立因果关联。服务商支持的幂等键与本地去重共同使用，不宣称数据库事务能保证外部动作恰好一次。

邮件发送成功仅表示当前已验证的发送阶段成功；没有收件回执时不写“收件人已收到”。签名结果须关联具体送签制品与签署流程。生产环境选择哪种签名实现需要另行核验，本设计不把发现签名类当作已验证真实签名链路。

### 5.6 后台任务直接写库及维护

所有受控写入入口均须携带 actor_type、稳定任务／服务身份、operation_id、受影响样本及实际输入摘要。绕过应用的 SQL、外部脚本和外部集群驱动无法靠应用埋点自动补齐；实施时应列出写入清单并改为受控接口／受控写入库。

确需保留直写时，应提供经过验证的数据库变更采集或受控脚本同事务审计作为补充，并解决操作者归因、删除前值、重放去重及缺失检测。binlog 本身不能补出业务意图和修改原因。在所有实际写入方完成接入前，只能报告“已覆盖的入口”，不能报告全系统历史完整。

审计证据无普通修改、删除、清空入口；应用数据库账户拒绝审计表 UPDATE、DELETE、TRUNCATE、DDL。查询索引或缓存可重建，证据不可被缓存清理任务删除。DBA 维护、保留到期处置、独立备份与防篡改归档须另走受控运维程序并留记录，不在本期增加审计删除接口。

## 6 如何查询

### 6.1 查询路径

先在授权范围内按全局唯一样本编号查询，得到已有 sample_file.id，再按 audit_event_subject 的 sample_id 或编号快照查事件，批量读取事件头和该样本明细。录单行已删除或尚未到达时，直接从审计编号快照定位事件和已有样本主键，不要求业务表查询成功。录单前事件通过编号快照纳入；发生过原业务编号更正时，依据同一 sample_id 的更正事件扩展旧号查询范围。主链查询不依赖 sample_file 当前是否存在，也不要求报告仍是最新版本。

直接从样本、流转或报告页面进入时传已授权的内部 id，由服务端解析唯一编号及样本主键；仍需重新检查权限，不能因为从业务页面跳转就信任前端传入的租户。原业务行被删除后，只要具有相应历史查看权限，仍可通过审计主体索引查询。

### 6.2 拟议只读接口

下列路径、权限均是本方案建议，尚未注册。Bigint id 和游标内的 id 均按字符串传输。租户范围由后端授权上下文决定，管理员跨药企筛选也须经过显式权限校验。

| 接口 | 主要参数与返回 | 拟议权限 |
| --- | --- | --- |
| GET /audit/samples | subbarcode 精确定位，列表可按 keyword、pageNum/pageSize 检索；返回样本编号、sampleId、来源与记录数 | audit:sample:list |
| GET /audit/samples/by-number | subbarcode 必填；返回唯一样本、当前摘要、存量基线、分析批次、报告及关联缺口 | audit:sample:query |
| GET /audit/events | subbarcode 必填；支持 stage、eventCode、outcome、analysisId、reportId、includeSampleCommon、时间、sort、cursor、pageSize；返回样本过程事件 | audit:sample:query |
| GET /audit/changes | auditScope、objectType、objectKey、操作人、动作、subbarcode、时间及游标；返回两类对象变更，不要求填写样本编号 | audit:change:list |
| GET /audit/events/{eventId} | 样本事件附 subbarcode 上下文；非样本事件按对象权限校验；返回授权明细与因果事件 | audit:event:query |
| GET /audit/samples/reports | subbarcode 必填；返回所有 analysisId／reportId、生成与签署制品、交付事件 | audit:sample:query |
| GET /audit/artifacts/{artifactId}/download | 校验样本与制品权限后读取受控文件；记录访问，不接受客户端文件路径 | audit:artifact:download |

不提供审计新增、编辑、删除、复核、还原 HTTP 接口。本期不实现通用审计导出；后续需要时独立设计权限、字段脱敏与导出行为留痕。

输入完整样本编号直接定位唯一履历，无同号多候选步骤；模糊搜索只用于样本列表，限制长度、页大小及频率。旧号查询通过已审计更正事件定位同一 sample_id，若更正历史缺失则明确提示，不能猜测。样本时间线默认按 (occurred_at, event_id) 升序进行键集分页，游标同时携带时间和 id；切换倒序同步反转两个字段。首屏返回 ceilingEventId，后续固定上界和排序／筛选，避免通常的新写入挤动分页；新增或延迟登记事件刷新后纳入。ID 分配与提交可能交错，ceilingEventId 不构成严格事务快照；有严格导出快照需求时须另行设计一致读取，本期不作此保证。变更记录列表默认同一组合倒序。时间筛选明确使用 occurred_at，recorded_at 另作登记时间筛选。

### 6.3 可见性与性能

audit:change:list 不自动授予跨租户或系统权限；非样本变更详情还须满足对象授权，平台范围的配置仅系统审计授权可见。样本编号全局唯一仍须检查所属药企权限。审计权限与原业务权限分别校验，范围至少为药企与当前已有的业务授权；未来增加项目／试验限制时同样下推到检索、统计、列表、详情与文件。批次标题和计数也不能暴露其他药企数据。多样本事件详情只返回当前样本明细：已录单按 sample_id，录单前明细按 subbarcode_snapshot 精确匹配；共享对象快照须有共享配置查看权限。

列表只返回短摘要、变化行数与字段数；展开事件才取 before／after。一页事件一次批量加载 subject 和统计，不按每个事件逐次查多张业务表。大 JSON 延迟加载，不截断后冒称完整；前端摘要截断时可展开全文。文件和快照按同一受控保留策略管理，审计保留不短于其需要支撑的业务记录。

当前样本摘要可来自最新授权业务数据或审计投影，但必须标为“当前信息”；事件详情使用当时快照。显示脱敏不应销毁原本必须保留的业务证据；敏感原值只在有授权的详情中返回，不在列表、URL、标题中输出。

## 7 在哪里与怎样展示

### 7.1 入口

建议新增“审计追踪”菜单，下设“样本履历”和“变更记录”。样本履历为独立页面，拟议路由 /audit/samples。输入唯一编号直接进入该样本；样本列表包含编号、药企、录单主键、来源摘要、分析次数、报告数和关联缺口，不显示同号样本选择器。

在现有 report/sample-info/index.vue、report/sample-flow/index.vue、质控列表及报告解读详情增加“查看履历”入口。样本流转行带 analysisId 进入时预选该批次，报告详情带 reportId 进入时预选该报告，同时允许切换“该样本全部历史”。这些均为拟议界面增量，当前未实现。

### 7.2 样本履历页面

页面顶部展示唯一样本编号、现有录单主键、所属药企和历史起点；录单尚未到达、缺失关联或启用前历史不完整须直接可见。发生过编号更正时展示其事件，不增加独立追踪号。

默认按操作时间由早到晚呈现一条线性履历，事件卡片标明数据v1／v2、analysis_id、report_id；切换版本只筛选视图，不改变事件本身。页面提供“全部过程”和“仅有字段变更”的筛选；质控导入但无字段变化可显示 NO_CHANGE 的实际处理结果，普通查看和页面跳转不产生虚假业务进展。

主体使用三个页签：“过程时间线”“报告与交付”“对象变更”。筛选区提供环节、操作、结果、操作人、来源、日期、分析批次和报告。筛选后的计数要标为当前条件范围，不能把少量事件当成完整履历。

时间线按事件展示，卡片包括动作、时间、操作者／来源、结果、分析批次、报告、摘要及变化数。展开后按对象／表分组，逐行查看业务主键与“字段、原值、新值、单位”。新增与删除显示完整受控快照；同一事件涉及多张表时只展示一次主动作。

过程是可循环、可失败的事实序列，不能用一条必然单向完成的进度条替代历史。现有瞬时态可在同一事件 context_json 中保存 transitions 数组，例如 41→43→50，界面显示“审核通过并发起签署”，同时保留最终数据库前后快照；不伪造不存在的独立已提交中间行。

### 7.3 设计示例

以下编号与数值仅为设计示例，非运行数据。录单主键 sample_file.id=101、全局唯一样本编号 S001；第一次上传为数据v1（A10），第二次上传为数据v2（A20）。表格按操作时间从早到晚排列，实际到达顺序可以不同，界面不强行按业务阶段重排。

| 顺序 | 环节与事件 | 页面可观察内容 |
| --- | --- | --- |
| 1 | 样本信息导入 | sample_file#101 新增，完整快照及来源批次 |
| 2 | 样本信息修改 | 旧值→新值；操作者及操作时间；属于样本公共事件 |
| 3 | 湿实验质控导入／更正 | 导入结果、原始指标、修改前后值和判定依据 |
| 4 | 干实验质控导入／更正 | 实际指标及判定变化；已知批次时关联 A10 |
| 5 | 上传数据v1及位点 | A10 + S001；原始文件主键、输入清单校验值、解析行新增／替换 |
| 6 | 数据v1报出选择与解读 | 是否报出前后值、实际报出位点集合、解读字段变化及依据 |
| 7 | 报告v1状态流转 | R30；认领／提交／退回／完成等真实起止状态、动作与操作者 |

“报告与交付”按数据版本 → 报告业务版本／report_id → generation_no 分组，再列 JSON／DOCX／PDF／签署件及发送尝试。显示“数据v1 → 报告v1 R30 第2次生成”，不把生成次数等同于报告业务版本。没有可信版本标签的旧记录按真实 analysis_id／report_id 显示并标明版本未知。文件下载指向历史制品，发送记录显示实际附件，不能只有一个“当前报告”链接。

### 7.4 交互状态与组件约束

沿用 Vue3／Naive UI、现有表格 hooks、分页、主题和抽屉规范，不引入新 UI 库。编号查询直接打开唯一样本；分析批次和报告筛选使用 NSelect。事件摘要、长字段值和多表明细可逐层展开，窄屏保留上下文并允许表格横向查看。

空状态区分“该样本无审计”“当前筛选无结果”“启用前仅有基线”“关联待确认”。请求失败允许重试，禁止以空数组吞掉异常；无权访问返回明确拒绝。已删对象仍显示快照，业务跳转不可用时提示已删除。字段值和导入文本按纯文本展示，不执行其中的 HTML 或脚本。无复核、还原、删除审计按钮。

### 7.5 变更记录页面

拟议路由 /audit/changes，输入为范围、模块、对象类型／主键、操作人、动作和操作时间；样本编号为可选条件。列表展示事件时间、范围、对象摘要、动作、操作人、来源、结果与变化数量，默认由新到旧。非样本记录的样本编号显示“不适用”，不设置必填样本条件；按具体用户／角色对象可查看连续变更历史。

展开事件后展示主表及关联表的字段前后值。创建、删除、角色绑定和授权变化均可查询；密码重置仅显示动作结果，不显示密码、哈希或 Token。无权限与无记录分别提示；审计入口不提供修改、删除、复核和还原按钮。样本相关记录可跳转该样本时间线，非样本配置变化不伪造样本关联。

### 8.2 存量迁移

先只读体检运行库：样本编号跨药企全局唯一是否落实、空编号、孤儿 analysis_id／report_id、跨租户关联、软删对象、外部源 id 冲突，以及仅剩最新路径的旧报告。体检结果不能由仓库 DDL 或模拟数据代替。

不分配新样本身份；沿现有 sample_file.id 与唯一样本编号回填审计关联，多分析和多报告保留各自真实主键。缺少录单信息的记录先按编号纳入，并明确显示关联缺口。基线在共同快照或暂停写入窗口获取，记录切换时点；并行运行时须制定水位与增量补齐方案，避免切换丢变更。

基线事件使用 BASELINE_IMPORTED，包含采集时间、来源表和当前快照。历史 create_time、update_time 仅作为来源元数据，不冒充过去每次修改。能够找到并校验的旧报告文件登记为 artifact_origin=LEGACY_IMPORT；无法证明生成顺序时 generation_no=NULL，缺失原始输入时 input_snapshot_ref=NULL，并在 dependencies_json 标明缺口。界面单独列出“历史导入，原版本未知”，不能把未知序号随意写成1。

### 8.3 分阶段交付

第一步核对跨药企全局唯一约束、上传版本契约和一条样本两次上传／两份报告的端到端实例。第二步实现四表、事件范围、统一写入与变更记录查询，以样本／质控和用户／角色的多表变更验证事务及权限。第三步接入位点上传／报出、解读、状态流转、报告版本和交付，形成按操作时间排序的样本完整履历。第四步核对全部实际写入方、存量基线及权限后再声明已覆盖范围。

本期结束标准是声明范围内的新增、修改、删除和过程都能查询，并能解释历史缺口；不以增加一个日志菜单代替业务入口接入。审计复核和还原不进入这四步验收。

| AT18 | 一个事件含多个样本 | 单样本视图无其他样本敏感明细，事件只出现一次 |
| AT19 | 删除业务行、改用户昵称、改模板名 | 历史仍可查；历史名称和输入快照保持当时含义 |
| AT20 | 相同毫秒、延迟登记和翻页期间新增事件 | 按 occurred_at＋id 稳定排序和组合游标；刷新纳入新事件；明确非严格事务快照 |
| AT21 | 原始报告文件缺失 | 显示不可用，不下载当前版本替代 |
| AT22 | 应用账号修改或清空 audit 表 | 数据库权限拒绝；无普通维护接口可绕过 |
| AT23 | 存量基线与关联缺口 | 明确显示上线前不完整，不生成虚构历史事件 |
| AT24 | 超过 JavaScript 精确整数范围的 id | API 与路由完整保留字符串 id，无错样本或错报告 |
| AT25 | 新模块新增写入入口 | 接入清单与事务用例同步，未接入不能声明覆盖 |
| AT26 | 另一药企试图新增已存在编号 | 全局唯一业务规则拒绝；不能依赖 tenant_id 联合唯一放行 |
| AT27 | 创建用户并分配角色 | 一个 NON_SAMPLE 事件；用户和角色绑定逐条明细；不要求样本编号 |
| AT28 | 修改角色及替换菜单权限，随后撤权 | 主表前后值与实际关系增删齐全；各已提交动作独立可查 |
| AT29 | 密码重置 | 保存执行者、对象、时间和结果；审计中无密码、哈希、Token或会话内容 |
| AT30 | 样本导入、质控、位点、状态与解读连续操作 | 一条按操作时间排序的履历；每次修改前后值、报出位点和状态起止值完整；公共事件不伪挂某版本 |
| AT31 | 同产品同日再次上传或原路径文件被覆盖 | 不静默覆盖旧数据版本；保留原输入证据，正确区分新版本与同版本重解析；契约不明时明确关联缺口 |

需求映射：AUD-01 对应 AT01、AT15、AT19、AT20、AT23、AT30；AUD-02 对应 AT06—AT14、AT17、AT18、AT27—AT29；AUD-03 对应 AT02—AT05、AT09、AT15、AT16、AT26、AT31；AUD-04 对应第4—8章及 AT21—AT25。

## 10 实施前确认与扩展边界

已确认：subbarcode 跨药企全局唯一；同一样本多份数据按 analysis_id + subbarcode 关联；记录样本相关和非样本修改，并按操作时间查询样本流转解读履历。暂定 file-v1 → report-v1、file-v2 → report-v2。实施前需核对全局唯一数据库约束及规范例外、相同产品同日重传如何形成独立数据版本、v1／v2标签分配和存量同分析多报告的处理口径、原业务是否允许编号更正；还须核对上游幂等消息号、运行库孤儿、外部写库边界、非样本对象完整清单、可见范围与敏感原值权限、文件及审计保留策略。这些不阻止本版方案评审，但不能在实现中用猜测补齐。

本期不要求所有新增／自动同步都弹出“修改原因”。沿用已有业务原因，自动任务记录来源和规则依据；哪些人工关键更正必须填原因在业务确认后再约束，不能借审计设计无依据增加审批流程。

未来复核可建立引用 event_id 与范围水位的独立记录；未来还原须重新检查权限、状态、外部副作用与兼容性，并以新的业务写入产生审计，不能篡改旧事件。本期不实现上述服务，也不承诺现有快照可自动恢复所有数据。
