# 样本审计追踪功能说明书

本模块在“合规管理 → 数据审计”下提供变更记录和样本履历两个只读视图。样本信息、质控、解读、报告和用户角色等已接入操作，在业务事务内保存实际记录的修改前后值，供运营、开发、测试和质量人员追查事实。

本版按已经实现并部署在本机的两表方案修订，替代 V0.3 中未落地的四表建议。说明书保留原文件名、章节和需求编号；模块菜单名称为“数据审计”。本文是实现说明与测试依据，不代表业务验收签字或 GxP 合规认证。

## 1 目标与边界

### 1.1 已确认目标

AUD-01：按唯一业务编号 subbarcode 查看一个样本在已接入模块中的录入、质控、解读和报告流转历史，按操作时间组合成可查询的履历。外部直接写库的缺口在第10章说明。

AUD-02：记录样本相关及非样本对象的新增、修改、删除和关系变化，保存操作者、时间、结果、真实主键及字段前后值。当前非样本范围为用户、角色及其授权关系；其他配置需逐项接入。

AUD-03：业务约定 subbarcode 跨药企全局唯一；同一样本多份数据通过 analysis_id 与 subbarcode 区分，报告通过 report_id 关联。审计保留已有真实关系，不重新分配数据或报告版本。

AUD-04：明确数据如何存储、入口如何接入、如何查询、在哪里展示，以及如何验证。模块仅留痕和查询，不新增审计审批或业务恢复功能。

### 1.2 本期范围

已实现自动记录、两类查询、前后值详情、租户隔离、事务失败共同回滚及有限的外部调用过程记录。样本公共事件不强行绑定某个 analysis_id。用户和角色事件不填虚构样本编号。

本期没有审计复核、审计签批、导出、历史还原、独立制品历史表、存量基线回填、通用事件溯源平台或数据库防篡改存储。业务原有审核、签署和发送动作继续由原模块执行，审计只记录已接入的持久化变化和过程事实。

### 1.3 版本变化与阅读方式

| 原方案 | 当前实现 | 影响 |
| --- | --- | --- |
| 四张建议表 | audit_event 与 audit_change 两表 | 不建 audit_event_subject、audit_report_artifact |

| 全覆盖、存量基线与外部证据闭环 | 明确已接入入口，上线后新增记录 | 不把缺失的上线前历史写成真实审计 |
| 目标与待实施用例 | 目标、实现、历史执行证据分别列示 | 历史通过不等于本次重新执行或正式验收 |

### 2.2 当前实现与目标的关系

后端是 Java 与 Spring Boot，数据库是 MySQL 8，前端是 Vue 3 与 Naive UI。通用操作日志继续保留；数据审计独立保存受控前后值，并与业务事务一起提交。

不能对当前业务表的 update_time 做事后汇总来代替历史，也不能用流转页“最新报告”覆盖一个样本的旧报告事件。已提交审计不依赖业务行继续存在，操作者名称在事件产生时保存，不随之后的昵称变化回写。

## 3 样本编号与关联设计

### 3.1 唯一业务标识与真实主键

subbarcode 是用户确认的全局唯一样本编号。sample_file.id、analysis_data.analysis_id、analysis_report.report_id、文件及位点主键仍各有用途，不相互替代。审计没有新增样本主表，也没有给全部业务表增加 sample_id。

当前样本业务 DDL 的唯一键包含 tenant_id 与 subbarcode，查重也受现有租户条件影响；本次审计迁移没有新增跨药企全局唯一索引。因此“跨药企全局唯一”是已确认业务约定，不能据此宣称数据库已具备全局硬约束。详见第10章。

### 3.2 关联与授权

事件从实际业务记录取得 tenant_id、subbarcode、analysis_id 和 report_id；前端传入编号不等于获得访问权。样本与质控公共阶段没有分析 ID 时保留为空；用户、角色等非样本操作的样本关联为空。

普通用户按当前药企查询，平台超级管理员沿用既有跨药企权限。共享角色定义等平台事件使用既有平台日志标识 __platform__；不因为拥有数据审计查询权限而升级为平台管理员。签署联调回调保持原有租户范围，不能用别家签署流程号改变别家报告。

### 3.3 生命周期规则

| 场景 | 当前记录方式 | 限制 |
| --- | --- | --- |
| 同编号重复导入 | 对真实旧行和最终行做差异；无业务变化可记录 NO_CHANGE | 不凭请求参数判定已修改 |
| 已删除行恢复 | 记录 RESTORE；真实删除后新增则分别记录旧行和新行 | 原业务是否允许恢复由原模块决定 |
| 业务行删除 | 保留已写入的审计快照 | 不级联删除审计 |
| 同样本多份分析数据 | 按 analysis_id 区分，公共事件可一起查询 | 不把公共质控复制挂到每个批次 |
| 样本编号修改 | 明细保留字段前后值，事件以记录的编号归属 | 没有别名表，旧新编号历史不自动合并 |
| 外部数据先到 | 仅已接入入口产生的事件可按已知编号关联 | 不自动捕获外部初次上传和直接 SQL |

### 3.4 数据版本与时间

业务意图仍是 file-v1 对应 report-v1、file-v2 对应 report-v2；一个样本可有多份数据。当前审计只保存实际 analysis_id 与 report_id，不自行推导 v1、v2，也不以文件名或列表序号代替版本。

同一 report_id 的多次生成属于生成轮次，不能自动视为新的数据版本。既有同一分析下的多份报告保持真实分支。样本履历按 occurred_at、id 升序；变更记录默认降序。occurred_at 是服务端采集的操作时间，不是外部声明时间，也不证明并发事务的全局提交先后。

### 3.5 两类修改与两个视图

变更记录统一列出 SAMPLE 与 NON_SAMPLE 事件。样本履历输入完整编号后，查看相同 subbarcode 的事件；按分析 ID 筛选时，页面固定包含该样本 analysis_id 为空的公共事件。接口允许关闭公共事件包含项。

一次采集内的多表变化可归并，按真实药企、样本、分析和报告归属拆成事件。operation_id 标识一组事务采集，不是外部幂等键；不同租户作用域可能各有 operation_id，不能假设跨药企批次只有一个事件或一个操作号。

## 4 数据存储设计

### 4.1 两张已实现表

| 表名 | 用途 | 关联关系 |
| --- | --- | --- |
| audit_event | 保存动作、操作者、时间、结果与业务关联 | 一条事件可有零条或多条变化明细 |
| audit_change | 保存实际表、主键、变化类型及前后值 | event_id 逻辑关联 audit_event.id |

关系由应用维护，没有数据库外键和级联删除。无变化导入、凭证操作或外部调用过程可以只有事件，没有字段变化明细。审计表不是业务当前状态表。

### 4.2 公共约束

两表均为 InnoDB，字符集 utf8mb4，排序规则 utf8mb4_general_ci；主键是自增 bigint。两表都有 tenant_id、创建与更新时间字段，不设 del_flag。默认 tenant_id 为 000000 是表结构默认值，实际归属仍由受控服务确定。

应用只提供审计查询接口，记录器只追加数据。本机应用的数据库账号仍具有现有权限；未配置独立的不可修改数据库账号、外部不可变存储或密码学防篡改链，不能把“页面只读”解释为“数据库管理员也不能改”。

### 4.5 枚举与含义

| 字段 | 当前值 | 含义 |
| --- | --- | --- |
| audit_scope | SAMPLE、NON_SAMPLE | 样本相关与非样本对象 |
| source | USER、SERVICE | 登录用户或服务上下文；无登录身份时使用 SYSTEM 标识 |
| outcome | STARTED、SUCCESS、FAILED、NO_CHANGE | 已发起、成功、失败、无业务字段变化 |
| change_type | CREATE、UPDATE、DELETE、SOFT_DELETE、RESTORE | 实际新增、修改、物理删除、软删除或恢复 |

SUCCESS 不等于收件人已收件，也不等于正式签署合规认证。凭证操作只记录事实，可能显示成功且变化记录数为零。过程调用的 FAILED 也不表示已经保存了外部数据库逐行差异。

## 5 新增修改删除如何持续留痕

### 5.1 写入位置与依赖

业务服务显式调用 AuditRecorder，不依赖通用请求日志或自动拦截所有 SQL。AuditSource 和 AuditTarget 只允许服务端声明的表名、主键及定位列；值使用绑定参数。仅把表加入白名单，不会自动完成该模块的审计接入。

### 5.2 事务与真实值

处理顺序为：原业务授权与校验 → 受控旧值快照 → 原业务写入 → 提交前读取最终值 → 比较并追加事件和明细 → 一起提交。快照读取对目标行加锁；审计写入失败时，业务和父事件一并回滚。

同一事务、同一作用域内嵌套调用合并采集，保留首次业务动作作为事件动作；跨租户作用域分别采集。afterCommit 的失败处置使用独立新事务。该机制不新增业务字段乐观锁，也不保证没有明确目标行的所有数据库写入都被捕获。

### 5.3 差异口径

按实际持久化值比较，区分 null、空串与零。create_time、update_time、create_by、update_by 等技术字段不构成业务差异；辅助关联列不进入业务快照。密码及其哈希、Token、密钥等凭证字段按受控规则排除，嵌套结构也执行清理。

有实际变化时逐条保存真实主键；成员关系替换体现为旧关系删除与新关系新增，不按数组下标配对。质控同值重导为每个样本保留 NO_CHANGE 事件，不因只有更新时间变化而漏掉导入事实。

### 5.4 批量与跨表

批次内事件归属来自真实行，避免把平台管理员当成数据所属药企。样本 Excel 导入按既有逐行事务处理，成功行形成审计，失败行按原接口约定返回；其他整批事务失败则共同回滚。不增加一套与原业务冲突的“审计部分成功”规则。

### 5.5 报告生成签署与交付

报告制品路径、模板及状态登记在实际修改前开始采集；版本序列表、历史匹配与复用记录等跟随相关业务事务记录。签署普通联调回调不得扩大租户访问范围。

文件渲染、外部签署和 SMTP 等外部副作用不因为数据库回滚就自动撤销。审计记录已接入的登记与结果；没有独立制品表或审计文件下载接口，也不提供任意历史时点制品还原。

### 5.6 外部任务与维护

文件重驱动及重新解读的外部扫描调用，记录发起与返回结果。外部扫描器直接写库、外部初次上传和人工 SQL 不会自动形成逐行前后快照。仅显示“调用成功”不能证明外部所有位点均已纳入审计。

新增模块必须核对真实表和主键、授权范围、事务边界及全部写入口，显式接入记录器，补充无变化、删除恢复、越权及共同回滚测试，并同步第8章清单。后台调用还须明确服务身份和所属药企。

## 6 如何查询

### 6.1 查询路径

列表直接读取 audit_event；详情先按当前租户与事件 ID 读取事件，确认可见后再读取 audit_change。不通过当前业务行重新拼接过去的字段值。字段详情中的 before、after 表示当时保存的受控快照。

### 6.2 已实现只读接口

| 接口 | 输入与输出 | 权限 |
| --- | --- | --- |
| GET /compliance/dataAudit/list | 分页条件；返回 rows、total 等现有 TableDataInfo 结构 | compliance:dataAudit:list |
| GET /compliance/dataAudit/{id} | 事件 ID；返回 event 与 changes | compliance:dataAudit:query |

列表参数：subbarcode 精确匹配；analysisId、reportId 精确匹配；auditScope 按范围匹配；action、actorName 模糊匹配；beginTime、endTime 限定操作时间；ascending 控制时间与 ID 的顺序。includeSampleCommon 只有同时提供样本编号与分析 ID 时，才会将该编号下 analysis_id 为空的事件纳入查询。

页码使用 pageNum、pageSize；服务端默认每页20条，并限制在1—200条。页面采用共享表格分页组件，初始页大小可能使用其统一默认值。客户端自定义排序列不直接拼入 SQL。无权限或不存在的详情返回现有业务异常“审计记录不存在或无权查看”。

### 6.3 可见性与查询限制

页面没有审计新增、修改、删除、恢复或导出接口。详情权限独立校验，不以列表按钮隐藏代替服务端授权。样本编号唯一也不解除药企隔离。

当前为普通页码分页，不实现 ceilingEventId、组合游标或查询快照。查询期间新增数据可能使后续页变化。后端有时间和报告 ID 条件，当前页面尚未提供对应控件；不写成现有界面功能。
