# 数据备份 数据库备份使用与运维文档

数据库备份（全量 + binlog 增量）的日常使用、巡检与恢复手册。系统里只有一个只读页面；备份本身由宿主机上的 Python 主控脚本 `backupctl` 执行，策略与凭据全部在 `conf/backup.yml`。

本文的读者是运维／实施人员：照着做能跑一次备份、看懂页面、判断备份是否连续、以及真的把库恢复出来。开发口径（为什么这么设计、字段取舍）见 `.hermes/plans/2026-10-29_162000-backup-db-v2.md`。

文中的命令都标注了执行位置：**宿主机** = 部署 biotech-plus 的 Linux 机器；**容器内** = `docker exec` 进入 `biotech-plus-mysql` 里执行。所有「实测」结论来自 2026-10-29 至 2026-10-30 在本机（dev 栈）的真实运行，日志路径随结论给出。

只想要最短上手卡（部署 4 步 + 命令表 + 故障速查），看同目录的 `数据库备份脚本使用说明-简版.md`（脚本目录 `backup/README.md` 指向它）。

### 3 2 mysql 段

| 键 | 当前值 | 说明 |
| --- | --- | --- |
| `use_docker` | `true` | `true` = 所有 MySQL 动作 `docker exec` 进 `container`；`false` = 用宿主机的 `mysqldump`／`mysqlbinlog`／`mysql`（此时 `container` 忽略，`host/port` 要写宿主可达地址） |
| `container` | `biotech-plus-mysql` | `use_docker=true` 时，所有 mysqldump／mysqlbinlog／mysql 都在这个容器里跑；也是上报的 `instance` |
| `host` / `port` | `127.0.0.1` / `3306` | 容器内连库地址，**不要写 localhost**（socket 与 TCP 混用会在容器里连错） |
| `user` / `password` | `root` / `root` | 直接写在文件里；上线前换成专用账号并 600 |
| `databases` | `[ry-vue, nkb]` | 绑定备份的一组库，必须非空且不重复 |
| `exclude_tables` | `ry-vue: []`、`nkb: []` | 按库排除表；空数组 = 全备。写法见 §3 6 |
| `full.schedule` | `Sun 02:00` | systemd `OnCalendar` 语法；`install` 时写进 timer |
| `full.type` | `weekly` | 写进 `backup_db_full.backup_type`；手工补跑用 `--type manual` 覆盖 |
| `full.retention.local_copies` | `8` | 本地保留份数（每周一次 ≈ 8 周） |
| `binlog.schedule` | `*-*-* 02:10:00` | 每天 02:10 |
| `binlog.retention.local_days` | `7` | 本地增量目录保留天数；必须小于 MySQL 的 `expire_logs_days`，否则服务端先删、补跑无数据 |
| `dump.zstd_level` | `19` | 宿主压缩级别；实测 `nkb` 79 MB → 11.4 MB 约 21 s（本机数据变小后全量 118 表压出 11.1 MB） |
| `dump.single_transaction` / `routines` / `triggers` / `events` | 均 `true` | `--single-transaction` 不锁表；其余保证视图外对象一起备 |
| `prune.schedule` | `Sun 04:00` | 清理定时 |
| `binlog_keep_warn_days` | `14` | 与 `@@expire_logs_days` 比较，小于它就告警（当前 7，所以 `check` 恒有一条 WARN） |

演练相关配置在**顶层 `drill` 段**（不再放在 `mysql.drill.suffix`，旧写法仍兼容读取）：

```yaml
drill:
  mysql:                      # 演练实例（推荐另一台机器）；整段留空 = 回落到 mysql（同实例换库名演练）
    host: 172.20.1.50
    port: 3306
    user: root
    password: FILL_ME
    client_container: biotech-plus-mysql   # 宿主机没有 mysql/mysqlbinlog 时，用它当客户端
  database_suffix: "_drill"   # 目标库 = <生产库名> + 后缀；禁止为空（空 = 覆盖生产库，脚本拒绝）
  drop_before_restore: true   # 每次演练先 DROP 目标库，两次演练不叠加
  verify_md5: true            # 恢复前校验实体 MD5
  allow_ddl_rewrite: false    # 跨库名回放会丢 DDL，默认拒绝
  keep_cache: false           # drill-cache 里从 OSS 下载的文件，成功后是否保留
  verify_tables:              # 恢复后（回放 binlog 之前）逐表比对「行数 + 最大主键」
    ry-vue:                   # 留空/不写 = 不校验，只判表数 > 0
      - sample_file
      - analysis_report
      - product_config
      - project_config
```

- `drill.mysql` 与 `mysql` 完全解耦：`db-full` / `db-binlog` 只读 `mysql`（生产），`drill` 只读 `drill.mysql`。
- 连接用标准 MySQL 客户端（`-h/-P/-u` + `MYSQL_PWD`）：宿主有 `mysql`/`mysqlbinlog` 就直接用，没有就 `docker exec` 进 `client_container`——**它只是客户端，连的是 `drill.mysql` 的 host/port**，与恢复目标是不是容器无关。
- 目标库每次先 `DROP DATABASE IF EXISTS <库名><suffix>` 再灌（`drop_before_restore: true`），两次演练不会叠加。
- `verify_tables` 是「恢复后到底对不对」的判据：全量备份时按这张表抓快照（行数 + 最大主键），恢复时在回放 binlog **之前**逐表比对（回放会改行数，所以必须卡在这个时点）。`--date` 取的是**当日归档的实际完成时刻**（02:10 触发 + 执行偏移），不是整点，否则会截掉这段归档尾部的数据。

### 3 3 oss 段

```yaml
oss:
  enabled: false                 # 当前状态：只落本地
  provider: aliyun
  endpoint: oss-cn-hangzhou-internal.aliyuncs.com
  bucket: FILL_ME
  access_key_id: FILL_ME
  access_key_secret: FILL_ME
  prefix: backup/prod            # 对象路径 = <prefix>/db/full_<日期>.sql.zst
  meta_md5_key: x-oss-meta-file-md5
  part_size_mb: 64
  threads: 4
```

- `enabled: true` 但四项凭据有缺 → 配置校验直接 `exit 2`，不会跑半截。
- 上传后会 `head_object` 回读自定义元数据里的 md5，与本地 md5 不一致即算失败（失败只写日志、不入库）。
- 全量走单对象上传，增量走 `upload_dir`（每个 binlog 文件一个对象，前缀 `<prefix>/db/binlog/<日期>/`）。
- `oss_days` 两个保留值只作为控制台生命周期规则的**建议值**，脚本不删 OSS 对象。

### 3 6 排除表的写法与实测结论

```yaml
exclude_tables:
  ry-vue: ["sys_oper_log", "tmp_*"]   # 精确名，或 * / ? 通配
  nkb: []
```

- 脚本先查 `information_schema` 把规则展开成实际表名（含视图），再逐个转成 `--ignore-table=db.table`。
- 一条规则没命中任何表 → 该规则被忽略，日志写 `排除规则未命中任何表，已忽略`；不会报错，所以要自己看日志确认。
- 实测：给 `ry-vue` 排 2 张表，`table_count` 从 52 变 50；排一张不存在的表，mysqldump 仍 `exit=0`（这就是「脏配置看不出问题」的原因）。
- 每份全量都会记录展开后的 `excluded_tables`，页面「表数(排除)」显示 `已备/库总数 (-排除数)`，恢复时先看这一列判断缺哪些表。
- 只建议排日志／流水／缓存类表。业务表排除后恢复出来的库就是缺表的。

## 4 命令速查

所有命令在**宿主机**执行，统一入口：

```bash
cd /home/liushangzhi/docker/biotech-plus/backup
./venv/bin/python backupctl.py <子命令> [参数]
```

| 子命令 | 做什么 | 定时 | 建议频率 |
| --- | --- | --- | --- |
| `db-full` | 展开排除表 → `mysqldump` 出一份包 → 宿主 zstd → md5 → OSS（可选）→ 上报 | `full.schedule` | 每周 |
| `db-binlog` | 从上次终点拉到本次 `SHOW MASTER STATUS` 的 binlog 文件 → OSS（可选）→ 上报 | `binlog.schedule` | 每天 |
| `prune` | 删本地过期全量（并上报 `local_pruned=1`）、过期增量目录、过期日志 | `prune.schedule` | 每周 |
| `check` | 校验 yml + timer 漂移 + `expire_logs_days` 余量 + 待补报积压 | `check.schedule` | 每天 |
| `install` | 按 yml 生成 `backup@.service` 与 4 个 timer，并打印启用命令 | 手工 | 发版／改 schedule 后 |
| `drill` | 按日期恢复到**独立演练 MySQL**：选全量 + 回放 binlog 到目标时刻，先校验实体再 DROP 灌库 | 手工 | 每月／验收前 |

退出码：`0` 成功；`2` 配置校验不通过（没做任何备份）；`3` 巡检发现问题（部分异常）；`4` 执行失败（全量／增量／演练）。

**日志才是明细**：命令的 stdout 只有一行 `exit=N | summary`，实际内容在 `log/<job>/<日期>.log` 与 `log/backup.log`。行格式固定为 `<时间> | <job> | <级别> | k=v ... | <消息>`。

### 4 1 db-full（全量）

```bash
./venv/bin/python backupctl.py db-full                          # 定时任务用的形态（trigger=timer，type 取 yml）
./venv/bin/python backupctl.py db-full --type manual            # 手工补跑，记录类型写 manual
./venv/bin/python backupctl.py db-full --date 2026-10-30        # 指定归档日期（落盘文件名与记录日期）
```

执行顺序（每一步都能在日志里看到结果）：

1. 展开排除表，`WARN` 提示未命中的规则；
2. 容器内 `mysqldump --single-transaction --routines --triggers --events --master-data=2 --flush-logs --set-gtid-purged=OFF --skip-add-locks --databases ry-vue nkb [--ignore-table=…]`，输出到 `work_root/db/full_<日期>.sql`；
3. 从 dump 头部的 `-- CHANGE MASTER TO` 行取基线 `binlog_file` / `binlog_pos`；
4. 宿主机 `zstd -19 -T0 --rm` 压缩并算 md5；
5. `oss.enabled=true` 时上传并回读 md5；
6. 上报 `POST /backup/db/full`（失败落 `state/pending-report/`，下次任一子命令启动时补报）；
7. 写 `state/full-baseline.json`（这份基线是「第一次跑增量」的起点）与 `state/full/<日期>.json`（历史 metadata：包名/路径/OSS key/md5/size/基线位点/表数，`drill` 靠它按日期找全量）。

`--flush-logs` 会让 MySQL 切一个新 binlog，所以每份全量记录的基线位点通常是「新文件 @ 154」，这是正常现象，不是位点错乱。

实测输出（`log/db-full/2026-10-29.log`，绑定备份版本）：

```text
2026-10-29T17:52:28+08:00 | db-full | INFO  | trigger=manual pid=883925 cfg=499edf8f script=unknown host=app-01 | start
2026-10-29T17:52:53+08:00 | db-full | INFO  | api=/backup/db/full | 上报成功
2026-10-29T17:52:53+08:00 | db-full | INFO  | scope=ry-vue,nkb tables=118/118 excluded=0 zst=11.1MB md5=54a2a836 binlog=mysql-bin.000010@154 dur_ms=24178 oss=off | ok
```

读法：`tables=已备表数/库实际表数`、`excluded=排除表数`、`zst=压缩包大小`、`md5` 前 8 位、`binlog=基线位点`、`dur_ms` 总耗时、`oss=off` 表示未上传。

### 4 2 db-binlog（增量）

```bash

```

执行顺序：

1. 起点 = `state/binlog-pos.json` 的 `file/pos`；若还没有增量记录，取 `state/full-baseline.json`（没有基线直接报错：「先跑一次 db-full」）；
2. 终点 = 当前 `SHOW MASTER STATUS`；
3. `SHOW BINARY LOGS` 取文件清单，算出 `[起点文件 … 终点文件]` 区间；
4. **逐文件**在容器内 `mysqlbinlog --read-from-remote-server --raw --start-position=<首个用起点位点，其余用 4>`，落到容器 `/tmp/bk-<日期>/`；
5. 清空宿主目标目录里的旧 `mysql-bin.*` 后 `docker cp` 取回，并断言「实际文件列表 == 区间列表」，不一致直接失败、不入库；
6. `oss.enabled=true` 时按文件上传；
7. 上报 `POST /backup/db/binlog`，写 `state/binlog-pos.json` = 本次终点，并写 `state/binlog/<日期>.json`（区间 `[start,end]` + 每个文件的 size/md5/本地路径/OSS key，同一天多次归档会合并成一个区间）。

### 4 6 drill（恢复到独立演练库 = 全量 + binlog）

```bash
./venv/bin/python backupctl.py drill                            # 恢复到最新可恢复点（最后一段归档的完成时刻）
./venv/bin/python backupctl.py drill --date 2026-10-29          # 恢复到 2026-10-29 02:10 归档点
./venv/bin/python backupctl.py drill --to "2026-10-29 18:00:00" # 恢复到精确时刻（优先于 --date）
./venv/bin/python backupctl.py drill --date 2026-10-29 --check-only   # 只出计划+校验实体，不 DROP 不恢复
./venv/bin/python backupctl.py drill --date 2026-10-29 --keep-cache   # 保留从 OSS 下载到 drill-cache 的文件
```

`--date` 的语义是「恢复到**那天归档完成的那一刻**」：归档 cron 在 02:10 触发，实际开始/结束带执行偏移（例如 02:10:07~02:10:15），所以目标时间取当天归档记录的 `finishedAt`，当日没有归档记录时才回落到 `02:10:00`。按整点截会把这段归档尾部的数据截掉。要更晚的时刻用 `--to`。完整流程：

```text
目标时刻 T
  → 在 state/full/ 里挑 date <= T 且实体可用、后续 binlog 链完整的最近一份全量（拿不到就退到更早的一份）
  → 从 full 的基线位点开始，按 [startedAt, finishedAt] 挑出连续 binlog 段，直到覆盖 T
  → 每个 full / binlog 文件按「本地 → OSS → 缺失」确认可得（缺一个就 FAIL，此时还没 DROP）
  → safety_check：suffix 非空 + 目标库名 != 生产库名 + server_uuid 比对
  → 下载缺的实体到 <work_root>/drill-cache/
  → DROP <库名><suffix> → 灌 full（sed 改库名）
  → verify_tables：逐表比对「行数 + 最大主键」（必须在回放之前，回放会改行数）
  → 逐库逐文件回放 binlog（首文件用基线位点，最后一段 --stop-datetime=T）
  → 校验：目标库存在、表数 > 0（**不和当前生产比表数**，历史恢复本来就该比现在少）
  → 写 state/drill/<目标日期>.json（成功失败都写）
```

几条硬规则（本机实测过，都是踩出来的）：

| 规则 | 说明 |
| --- | --- |
| 只有实体才算可恢复 | metadata 里有日期 ≠ 能恢复。本地没有就查 OSS，两边都没有 = `MISSING` → FAIL |
| 全量快照不能晚于目标时刻 | `--date D` 只挑「日期 <= D 且完成时间 <= D 02:10」的全量；拿更晚的快照恢复更早时间点会静默得到更晚的数据，所以直接拒绝 |
| 恢复到 D 日更晚时刻要用 D+1 的归档段 | `--date D` 只看 D 日 02:10；用 `--to "D 23:59:59"` 这类目标时，需要 D+1 凌晨那次归档，没有就报「超出已归档窗口：最后一段只到 X」 |
| 全量后的第一段要裁剪 | 全量 `--flush-logs` 切新文件，而增量仍从旧终点拉，所以某段会横跨「全量前/后」；用 `--start-position=<基线位点>` 只回放全量之后的事件，避免重复回放 |
| 段与段必须衔接、段内文件编号必须连续 | 上一段 end != 下一段 start、或段内缺 000125 这类，都直接 FAIL 并指出缺的文件 |
| 跨库名回放不碰 DDL | `--rewrite-db` 只改 ROW 事件，DDL（Query 事件）会被丢掉；先扫段内是否含 DDL，含则拒绝（除非 `allow_ddl_rewrite: true`） |
| 不许覆盖生产库 | `drill.database_suffix` 为空、或目标库名等于生产库名 → 直接拒绝，不执行任何 DROP |
| 一次演练不叠加 | 每次先 `DROP DATABASE IF EXISTS` 再灌；第二次恢复另一个日期会重建，而不是往旧库里加 |
| 业务表要逐表对上行数与最大主键 | `drill.verify_tables` 里的表，恢复后（回放前）`COUNT(*)` 与数值主键 `MAX()` 必须与全量快照一致；maxId 少了/多了都 FAIL，只有「maxId 相同、行数略少」是 WARN（快照比 dump 晚几秒） |

## 5 定时任务与启用

当前状态（实测）：timer 文件已生成在 `~/.config/systemd/user/`，但**四个 timer 都是 disabled**，未设 linger。要真正跑起来，按下面三条在**宿主机**执行：

```bash
systemctl --user daemon-reload
systemctl --user enable --now backup-db-full.timer backup-db-binlog.timer backup-prune.timer backup-check.timer
loginctl enable-linger "$USER"          # 未登录也要跑（timer 在用户会话外触发）
```

验证：

```bash
systemctl --user list-timers --all | grep backup     # NEXT 列有时间、LAST 为空表示已装上还没触发
grep -H OnCalendar ~/.config/systemd/user/backup-*.timer   # 与 yml 的 schedule 逐条对照
systemctl --user start backup@db-full.service        # 手工触发一次（等价于 backupctl db-full）
journalctl --user -u backup@db-full.service -n 30    # 看 systemd 侧有没有报错
```

注意事项：

- `backup@.service` 是模板单元，`%i` 取实例名（`db-full` / `db-binlog` / `prune` / `check`）；不要写成 `backup@db-full` 之外的实例名。
- 改 yml 的 `schedule` 后必须重跑 `install` + `daemon-reload`，否则 timer 仍按旧的 `OnCalendar` 跑；`check` 每天会抓这种漂移。
- timer 之间靠时间错开（全量周日 02:00、增量每天 02:10、清理周日 04:00、巡检每天 09:00）。全量会 `--flush-logs`，所以**全量之后的第一条增量起点是新文件**，不必手工干预。
- 脚本没有内置 `flock`：并发靠 timer 的时间错开与人不要同时手工跑。要跑手工补跑，先确认没有正在执行的 job（`pgrep -af backupctl`）。

### 6 2 页面结构（实测截图 `.hermes/verify/20-backup-page.png`）

```text
数据备份 / 数据库备份
├ 搜索条（SearchCollapse，默认收起）：库名（下拉，ry-vue / nkb）、备份日期（范围）

   └ 页签② binlog 增量
       归档日期 / 起点 file@pos / 终点 file@pos / 文件数 / 大小 / 链 / 配置版本 / 操作(文件清单)
```

列与字段的对应（排查时按这张表回库查）：

| 列 | 字段 | 说明 |
| --- | --- | --- |
| 覆盖库 | `db_scope` | 绑定备份的一组库，显示 `ry-vue,nkb` |
| 表数(排除) | `table_count` / `db_table_total` | 显示 `已备/库总数`，有排除时追加 `(-N)`；口径是**基表（BASE TABLE）**，`nkb` 的 51 个视图不计入 |
| 压缩包 | `local_size` | 字节数格式化 |
| 基线位点 | `binlog_file` + `binlog_pos` | PITR 起点 |
| 本地 MD5 | `local_md5` | 压缩包 md5，与 OSS 元数据回读值应一致 |
| 本地 | `local_pruned` | `0` 在本地（绿）/ `1` 已清理（黄，表示本地删了、OSS 仍在） |
| 配置版本 | `config_hash` 前 8 位 | 这次执行用的 backup.yml 指纹，便于对「改了配置但没生效」 |
| 链 | `chainState`（后端现算） | `接上` 绿 / `链起点` 灰 / `未接上` 黄 |

「链」是后端按「本条起点 == 上一条（更早一天）终点」现算的，不是落库字段；页首那条会多查一行更早的记录来判定。**断链只做提示，不做任何自动补偿**。

「文件清单」抽屉读 `files_json`，逐行列出 `{file, size, md5}`；用于核对某一天的增量到底拉了哪几个 binlog。

## 7 产物与 state

### 7 1 产物目录

```text
<work_root>/
├── db/full_<YYYY-MM-DD>.sql.zst        # 全量，一组库一个包，含 CREATE DATABASE + USE
└── binlog/<YYYY-MM-DD>/mysql-bin.0000NN   # 增量：当天区间内的原始 binlog 文件
```

实测（2026-10-29）：`db/full_2026-10-29.sql.zst` 11.6 MB（11.1 MiB）；`binlog/2026-10-29/` 两个文件（3347 B + 609 B）。

产物文件名里的日期来自 `--date`（默认今天），**不代表 binlog 区间的真实时间**——真实区间看页面「起点／终点」或 `binlog-pos.json`。

### 7 2 state（比产物更需要保住）

```text
<脚本目录>/state/
├── full-baseline.json     # 最近一次全量的基线位点（第一次跑增量的起点）
├── binlog-pos.json        # 上一条增量的终点（下一条增量的起点）
├── full/<日期>.json       # 每份全量的历史 metadata（恢复按日期选它）
├── binlog/<日期>.json     # 每天增量的历史 metadata（区间 + 文件清单 + MD5）
├── drill/<日期>.json      # 每次恢复的结果留痕（成功/失败都写，含业务表逐表比对）
└── pending-report/        # 上报失败待补报的 JSON（每条一个文件）
```

`full/<日期>.json` 的关键字段（缺了就没法从这一天恢复）：

```json
{
  "date": "2026-10-26",
  "backupFile": "full_2026-10-26.sql.zst",
  "localPath": "/home/liushangzhi/backup/biotech-plus/db/full_2026-10-26.sql.zst",
  "ossPath": "backup/prod/db/full_2026-10-26.sql.zst",
  "md5": "6103aed0...", "size": 11594339,
  "binlogFile": "mysql-bin.000120", "binlogPos": 4,
  "scope": "ry-vue,nkb", "tableCount": 118, "finishedAt": "2026-10-26 02:00:30",
  "snapshotAt": "2026-10-26 02:00:31",
  "tables": {
    "ry-vue": {
      "sample_file":     {"rows": 35, "maxId": 2028},
      "analysis_report": {"rows": 21, "maxId": 23}
    }
  }
}
```

`tables` 就是 `drill.verify_tables` 指定的那几张业务表在**全量完成那一刻**的行数与最大主键；`maxId` 取的是数值型主键列（`analysis_report` 主键叫 `report_id`，不写死 `id`），没有数值主键的表记 `null`。

`binlog/<日期>.json`（同一天多次归档会合并成一个区间，files 取并集）：

```json
{
  "date": "2026-10-29",
  "startFile": "mysql-bin.000122", "startPos": 1234,
  "endFile": "mysql-bin.000123", "endPos": 4567,
  "startedAt": "2026-10-28 02:10:09", "finishedAt": "2026-10-29 02:10:15",
  "files": [
    {"name": "mysql-bin.000122", "size": 3347, "md5": "198f0f62...", "localPath": "...", "ossPath": null},
    {"name": "mysql-bin.000123", "size": 609, "md5": "f98bb13f...", "localPath": "...", "ossPath": "backup/prod/db/binlog/2026-10-29/mysql-bin.000123"}
  ]
}
```

- `binlog-pos.json` 丢了 = 增量链起点丢失：脚本会退回用 `full-baseline.json`，于是**从最近全量重拉**一遍 binlog（文件会重复，但链不会缺段）。
- `full-baseline.json` 也丢了 = 必须先跑一次 `db-full`，否则 `db-binlog` 直接报错退出。
- `full/<日期>.json` / `binlog/<日期>.json` 丢了 = 那一天**不能按日期恢复**（即使包还在本地/OSS）；它是 `drill --date` 的唯一索引。
- state 故意放在脚本目录而不是 `work_root`：产物可以按策略删，位点链与 metadata 必须跟脚本一起备份／迁移。
- `prune` 只删本地产物与日志，**不删 metadata**：本地删了但 OSS 还在，仍然可以恢复。

## 8 恢复

恢复比备份更该手工做。以下每条命令都在**宿主机**执行，除了明确标注「容器内」的。恢复会覆盖数据，先停应用再动手。

### 8 1 恢复前必须确认的四件事

1. **包里有几个库**：当前绑定 `ry-vue,nkb` 一个包。dump 自带 `CREATE DATABASE IF NOT EXISTS` + `USE`，所以恢复会直接写这两个库。
2. **目标库是否已存在**：dump 不会 `DROP TABLE`；目标库里已有同名表时 `CREATE TABLE` 会报错（`--force` 会跳过建表继续插数据，结果是脏库）。**恢复前先明确是「覆盖现网」还是「恢复到临时库名」**。
3. **缺哪些表**：看页面「表数(排除)」与 `excluded_tables`，被排除的表恢复后不存在。
4. **恢复到哪个时间点**：全量只能恢复到「基线位点那一刻」，之后的数据要靠 binlog 回放到目标位点（§8 4）。

### 8 2 全量恢复到临时库（演练／核对，最常用）

把包里的库名换成新名字，灌进一个不冲突的库：

```bash
cd /home/liushangzhi/docker/biotech-plus/backup
PKG=/home/liushangzhi/backup/biotech-plus/db/full_2026-10-29.sql.zst

# 宿主机：先清掉同名临时库（不存在也无妨）
docker exec -i -e MYSQL_PWD=root biotech-plus-mysql mysql -uroot -e \
  'DROP DATABASE IF EXISTS `ry-vue_restore`; DROP DATABASE IF EXISTS `nkb_restore`;'

# 宿主机：解压后把库名替换成 *_restore，管道进容器里的 mysql
zstd -dc "$PKG" | sed -e 's/`ry-vue`/`ry-vue_restore`/g' -e 's/`nkb`/`nkb_restore`/g' \
  | docker exec -i -e MYSQL_PWD=root biotech-plus-mysql mysql -uroot --default-character-set=utf8mb4
```

口令一律走 `-e MYSQL_PWD=…` 传给容器：宿主机没有 mysql 客户端，容器里也没有导出 `MYSQL_PWD` 环境变量，所以 `docker exec … sh -c 'mysql -p"$MYSQL_PWD"'` 这种写法会因变量为空而报错。

`backupctl drill` 做的就是这件事（目标名 `<库名>_drill`），日常核对直接用 `drill` 更省事。恢复到临时库后跑一遍表数比对：

```bash
docker exec biotech-plus-mysql mysql -uroot -proot -N -e "
SELECT table_schema, COUNT(*) FROM information_schema.tables
WHERE table_schema IN ('ry-vue','nkb','ry-vue_restore','nkb_restore') GROUP BY 1;"
```

### 8 3 全量恢复到现网（覆盖）

```bash
# 1) 宿主机：停应用，避免恢复期间继续写入
docker stop biotech-plus-backend

# 2) 宿主机：确认要恢复的包与记录一致（包名、md5、基线位点）
ls -l /home/liushangzhi/backup/biotech-plus/db/
md5sum /home/liushangzhi/backup/biotech-plus/db/full_2026-10-29.sql.zst   # 与页面「本地 MD5」比对

# 3) 宿主机：覆盖前先留一份当前库（防止恢复选错包）
docker exec -e MYSQL_PWD=root biotech-plus-mysql mysqldump -uroot --single-transaction --databases `ry-vue` nkb > /tmp/before-restore-$(date +%Y%m%d-%H%M).sql

# 4) 容器内：DROP 两个库（dump 只会 CREATE IF NOT EXISTS，不会清旧表）
docker exec -i -e MYSQL_PWD=root biotech-plus-mysql mysql -uroot \
  -e 'DROP DATABASE IF EXISTS `ry-vue`; DROP DATABASE IF EXISTS `nkb`;'

# 5) 宿主机：灌入
zstd -dc /home/liushangzhi/backup/biotech-plus/db/full_2026-10-29.sql.zst \
  | docker exec -i -e MYSQL_PWD=root biotech-plus-mysql mysql -uroot --default-character-set=utf8mb4

# 6) 宿主机：起应用
docker start biotech-plus-backend
```

注意：

- 第 4 步 DROP 之后到第 5 步灌完之前，系统是不可用状态；`ry-vue` 里含 `sys_user`／`sys_menu`，登录也会失效直到灌完。
- dump 里不含 `DROP DATABASE`，所以**不能靠「直接灌」覆盖**，必须先 DROP 或灌到新库名。
- 恢复后 `backup_db_full` 表里恢复的是备份时间点的数据，**备份记录本身也会回退**（新备份还没发生）。恢复完成后先跑一次 `db-full`，再让 timer 继续。

### 8 4 按时间点恢复（PITR：全量 + binlog 回放）

目标：恢复到「全量基线位点 → 某个时间点」。这是唯一能救「误删数据」的路径。

**首选：让脚本做**。`drill` 已经实现完整的「挑全量 → 校验实体 → 裁剪/衔接 binlog → 回放 → 校验」，把结果灌进演练库：

```bash
./venv/bin/python backupctl.py drill --date 2026-10-29 --check-only   # 先确认这个日期可恢复
./venv/bin/python backupctl.py drill --date 2026-10-29                # 灌进 <库名>_drill
```

它做的判断比手工稳：实体是否真的在（本地→OSS）、段是否衔接、段内文件是否连续、全量后的段是否按基线裁剪、目标时间是否超出已归档窗口、跨库名是否会丢 DDL、是否在 DROP 生产库。细节见 §4 6。

**手工兜底：恢复到现网（库名不变）**。以下命令在宿主机执行，用于「演练确认可行后，真的把生产库恢复到某个时刻」：

**第一步：确认区间**（页面或库）

```bash
# 全量记录的基线位点（PITR 起点）
docker exec biotech-plus-mysql mysql -uroot -proot -e "
USE \`ry-vue\`; SELECT db_scope, backup_date, binlog_file, binlog_pos FROM backup_db_full ORDER BY id DESC LIMIT 3;"

# 增量归档的区间（终点 = 可回放到的最远位置）
docker exec biotech-plus-mysql mysql -uroot -proot -e "
USE \`ry-vue\`; SELECT backup_date, start_file, start_pos, end_file, end_pos, file_count FROM backup_db_binlog ORDER BY id DESC LIMIT 5;"
```

**第二步：先做全量恢复**（§8 3，做到第 5 步、先不起应用）。

**第三步：回放 binlog**。binlog 归档在宿主 `<work_root>/binlog/<日期>/`，用管道喂给容器里的 mysql。下面是生产形态（库名不变）：

```bash
BIN=/home/liushangzhi/backup/biotech-plus/binlog/2026-10-29
START_POS=154                      # = 全量记录的 binlog_pos（首个文件的起点）
STOP_DT='2026-10-30 10:00:00'      # 要恢复到的时间点（不按时间就换成最后一个文件的 --stop-position）

idx=0
for f in $(ls -1 "$BIN"/mysql-bin.* | sort); do
  pos=$([ "$idx" -eq 0 ] && echo "$START_POS" || echo 4)
  # 一个库一条 mysqlbinlog：多个 --database 里只要有一个在当前段没事件，
  # MySQL 5.7 的 mysqlbinlog 会把整个输出过滤成 0 条（且 mysql 仍 exit 0）。
  for db in 'ry-vue' 'nkb'; do
    docker exec -i biotech-plus-mysql mysqlbinlog --database="$db" \
        --start-position="$pos" --stop-datetime="$STOP_DT" - < "$f"
  done
  idx=$((idx + 1))
done | docker exec -i -e MYSQL_PWD=root biotech-plus-mysql mysql -uroot --default-character-set=utf8mb4
```

四条硬约束（前三条是逻辑要求，第四条是本次实测踩到的坑）：

1. **首个文件用全量基线位点，后续文件用 `--start-position=4`**。位点只对「它所在的那个文件」有效，所有文件都用同一个起点会漏掉中间文件的头部事件。
2. **按时间点恢复优先用 `--stop-datetime`**（比手算位点稳）。要按事务定位时：`mysqlbinlog --base64-output=DECODE-ROWS -v <file> | grep -n -B2 -A5 'DELETE FROM'` 找到位点，再对**那一个文件**给 `--stop-position`。
3. **逐库回放，别把多个 `--database` 塞进同一条命令**：只要其中一个库在当前段没有事件，整条输出会变 0 条、`mysql` 还 exit 0（看着成功其实没回放）。
4. **不要在临时库上依赖 `--rewrite-db` 回放 DDL**（实测，见下）。要么回放到同名库，要么把 DDL 挑出来单独执行。

**实测：同名库回放可用，`--rewrite-db` 会丢 DDL**（2026-10-30，本机）

```text
① 容器内建探针表并插一行：CREATE TABLE pitr_probe(...); INSERT ...; FLUSH LOGS;
② 全量包 sed 改名恢复成 ry_vue_pitr / nkb_pitr（52 + 66 张基表），确认目标库没有 pitr_probe；
③ mysqlbinlog --database='ry-vue' --rewrite-db='ry-vue->ry_vue_pitr'
            --start-position=21663 --stop-position=22185 mysql-bin.000011
   → 输出里 CREATE TABLE 事件整条缺失（只剩 GTID/BEGIN/COMMIT 空壳），回放后目标库仍无该表；
④ 去掉 --rewrite-db，DROP TABLE pitr_probe 后回放同一段到同名库 ry-vue
   → 退出码 0，表与 1 行数据全部回来（id=1, note=pitr-verify）。
```

原因：`--rewrite-db` 只改写 ROW 事件的 `table_map` 里的库名；DDL 是 `Query` 事件（语句文本里带 `use ry-vue`），mysqlbinlog 不会改写它，于是按改名后的库过滤时把它整条丢掉了。所以：

- 恢复到临时库做**数据面**演练：全量包 sed 改名没问题；binlog 只回放纯 DML 的时间段可用 `--rewrite-db`，且表结构要预先在全量恢复里存在。
- 需要重放 DDL（建表/改表）的时间段：只能在同一库名上做（生产恢复就是这个形态），或在临时库里把 DDL 语句捡出来先执行。

### 8 5 恢复后必做的核对

| 项 | 命令／位置 | 期望 |
| --- | --- | --- |
| 表数 | `information_schema.tables` 按库统计 | 与包的 `table_count` 一致（排除表本来就少） |
| 业务表行数 | `state/drill/<日期>.json` 的 `verify_after_full.tables` | 每张表 `status=PASS`；有 WARN 说明快照比 dump 晚几秒，看差值是否合理 |
| 关键业务表 | `SELECT COUNT(*) FROM analysis_report;` 等 | 与恢复目标时间点的预期相符 |
| 备份记录 | 页面全量／增量两张表能打开 | 数据回退到备份时间点，属正常 |
| 应用 | `docker start biotech-plus-backend` 后登录 | 能登录、报告列表能打开（`sys_menu` 在 `ry-vue` 里） |
| 后续 | 手工跑一次 `./venv/bin/python backupctl.py db-full` | 日志出现「上报成功」，state 更新为新基线 |

## 9 巡检与故障处置

### 9 1 每日巡检清单（5 分钟）

1. `./venv/bin/python backupctl.py check` 看 `problems=` 与 WARN；
2. 页面 binlog 增量页签：最近一条「链」是 `接上` 或 `链起点`，**不能是 `未接上`**；
3. 页面全量页签：最近一条备份日期是上周日（或本周手工补跑的那天）；
4. `ls <work_root>/binlog/` 有当天日期目录；`ls -l <work_root>/db/` 份数不超过 `local_copies`；
5. `ls state/pending-report/` 为空（有文件说明上报失败，后端起没起）。

### 9 2 常见问题

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 页面「链」显示 `未接上` | 漏跑某天、手工改过 state、或同实例多套脚本各自写位点 | 看该条「起点」与前一条「终点」差在哪：若只是漏了一天，补跑会从当前 state 终点继续（**补不回历史那一段**）；要补历史必须用当时归档的 binlog 手工回放（§8 4） |
| 某天没有增量记录 | timer 没启用 / 机器关机 / 脚本失败 | 先看 `log/db-binlog/<日期>.log` 的 ERROR；`systemctl --user list-timers` 确认 timer 状态；修好后手工跑一次 |
| `db-binlog` 报「没有可用的起点」 | `state/` 被清过，且没有全量基线 | 先跑 `backupctl db-full`，再跑增量 |
| `db-binlog` 报「binlog 文件不在服务端列表里」 | 起点文件已被 MySQL 按 `expire_logs_days` 删除（当前 7 天） | 只能从最近一份全量重做链：跑 `db-full`（基线重置），此前的增量已无法补齐 |
| 日志 `上报失败，已落待补报` | 后端没起 / token 不匹配 / 路径不在 `api.token.tokens[].paths` | 修好后跑任一子命令，启动时会先 `flush_pending`；日志出现「补报完成 sent=N」 |
| 上报返回 401「客户端ID与Token不匹配」 | 少带 `clientid` 头，或 yml 的 `client_id` 与后端 `clientId` 不一致 | 两处对齐（§3 4） |
| 上报返回 403 | `sys_backup` 角色没有 `backup:db:report`，或 token 指向了别的账号 | 查 `sys_user_role` / `sys_role_menu`；脚本账号只应有「数据备份目录 + 上报」两条授权 |
| 上报返回 500「库名不能为空」 | 上报 payload 的 `dbScope` 为空（多见于手工改数据/旧版本脚本） | 用当前 `backupctl` 重跑；历史遗留按 400 类问题记日志即可 |
| 日志 `排除规则未命中任何表` | 配了不存在的表名/通配 | 核对表名大小写；这条不影响备份，但说明排除没生效 |
| `check` 报 `漂移：yml 与 timer 不一致` | 改了 yml 的 schedule 没重装 | `backupctl install` → `systemctl --user daemon-reload` |
| `check` 报 `timer 未安装` | 换了用户/机器，`~/.config/systemd/user` 下没文件 | 跑 `install` |
| `check` 恒报 `expire_logs_days=7 want=14` | MySQL 侧保留天数小于建议值 | 调大 `expire_logs_days`（要重启 MySQL 容器，见 §12） |
| `drill` FAIL 且 detail 显示源库表数 > 演练库 | 演练拿「当前库」当基准，全量包之后确实加过表 / 改过表 | 先跑 `db-full` 再 `drill`；只比基表数，不比数据行数（`nkb` 的 51 个视图不计） |
| `zstd: command not found` | 宿主机没装 | `apt install zstd`；不要在容器里装（脚本设计就是宿主压缩） |
| `oss2` 导入失败 | venv 里没装 | `backup/venv/bin/pip install -i https://mirrors.aliyun.com/pypi/simple/ -r requirements.txt` |
| 磁盘上涨 | 本地保留份数/天数偏大，或 drill 频繁 | `prune --dry-run` 看会删什么；全量 8 份 × 当前约 12 MB 量级很小，主要是 OSS 侧成本 |
| 容器改名 | yml `mysql.container` 与实际不符 | 改 yml 的 `container` 并重跑；`instance` 字段会跟着变，历史记录仍按旧实例名保留 |

## 10 账号与权限

| 项 | 值 | 说明 |
| --- | --- | --- |
| 上报账号 | `sys_backup` | 只用于脚本，不用于页面登录 |
| 角色 | `backup_bot`（`role_key`） | 授权恰好两条：目录「数据备份」+ 按钮 `backup:db:report`；**没有** `list` / `query` |
| 初始密码 | 见 `update_5.6.44-db-backup.sql` 注释 | 上线前必须改：后台「用户管理」重置，或改 `sys_user.password` |
| 页面查看角色 | 运维角色 | 需要 `backup:db:list`（菜单）+ `backup:db:query`（汇总）；只授页面不授父目录会 403 |
| token 覆盖 | `API_TOKEN_BACKUP` 环境变量 | 生产不要用仓库里的默认值 |

`sys_backup` 拿页面接口会被拒：带脚本 token 请求 `GET /backup/db/summary` 实测返回 HTTP 200 + `{"code":403,"msg":"没有访问权限，请联系管理员授权"}`；不带 token 返回 `{"code":401,...}`（HTTP 状态码都是 200，判据看 body 的 `code`）。这是设计：机器账号只能上报，不能看页面数据。

## 12 待确认事项与已知差异

1. **页面没有统计卡片**：`GET /backup/db/summary` 与 `Api.Backup.DbSummary` 已实现但页面未渲染（设计稿有 4 张卡片）。要么补卡片，要么删接口，需拍板。
2. **timer 未 enable、linger 未设**：属服务变更，需明确授权后执行 §5 三条命令；当前备份只有手工跑过。
3. **`expire_logs_days=7` < 建议 14**：改它要动 `deploy.sh` 两处并重启 MySQL 容器，会影响线上，待授权。
4. **OSS 未启用**：`oss.enabled=false`，`bucket`／AK 仍是 `FILL_ME`；代码已实现上传 + 元数据 md5 回读，拿到凭据改 true 即生效。**当前没有异地副本，本地删了就没有了**。
5. **表数口径是基表（BASE TABLE）**：`nkb` 实有 66 张基表 + 51 个视图，备份记录和页面「表数(排除)」都只算基表（dump 里 118 个 `CREATE TABLE`），恢复后 `information_schema` 的对象数是 117（含视图）。核对表数必须加 `TABLE_TYPE='BASE TABLE'` 过滤，否则会误判「备份漏了 51 张表」。
6. **脚本不在 git 里**：`backupctl` 与 `conf/` 放在 `docker/biotech-plus/backup/`，没有版本管理、没有异地副本。建议单独建仓（只提交脚本与 `.example`，`backup.yml` 永不入库）。
7. **老环境没有历史 metadata**：`state/full/`、`state/binlog/` 是本次改造（2026-10-30）才开始写；改造前的记录只有 `full-baseline.json` / `binlog-pos.json` 各一份，所以老日期无法 `drill --date`。`check` 会 WARN 提示。要覆盖更早日期，只能按 §8 4 手工回放。
8. **`prune` 不更新 binlog 的 `local_pruned`**：删除增量目录只删文件，不改 `backup_db_binlog.local_pruned`，页面「本地」列只对全量准确。
9. **`db-binlog --date` 不能补历史**：它只改落盘目录与记录日期，增量起点永远取 `state/binlog-pos.json` 的当前终点。漏跑那天的数据只能靠当时已归档的 binlog（或服务器上仍在保留期内的文件）手工回放；`drill --date` 是「恢复」，不是「补备份」。
10. **演练与增量共用实例时**：`drill` 的写入会进 binlog，撑大当天的增量包（实测 67 MB 里大部分是演练）。建议配独立 `drill.mysql`；同实例演练排低峰。
11. **`host` 标识与上报 `instance`**：`instance` 取 `mysql.container`（`biotech-plus-mysql`），`host`（`app-01`）只进日志。多实例部署时两者要不要都上库需确认（当前表里没有 host 列）。
12. **跨库名回放不能重放 DDL**：`--rewrite-db` 只改 ROW 事件。含 DDL 的时间段要恢复到演练库，只能用独立实例并把 `database_suffix` 置空（库名不变）。脚本默认拒绝，不静默丢表。
13. **`use_docker=false` 未在本机实跑**：本机没装 mysql 客户端，只用 stub 二进制验证了参数形态与逐文件落盘；真实 mysqldump／`mysqlbinlog --raw --result-file` 行为需要在装了 `mysql-client` 的机器上跑一次 `db-full` 确认（`check` 会先拦「缺命令」）。
