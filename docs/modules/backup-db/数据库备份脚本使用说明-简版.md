# 数据库备份脚本使用说明（简版）

面向运维的最短上手卡。完整口径（字段、页面、PITR 细节、17 条故障处置）见 `docs/modules/backup-db/数据库备份使用与运维文档.md`。

脚本做的事：每周全量（一组库一个压缩包）+ 每天 binlog 增量归档 + 本地清理 + 每日巡检 + 恢复演练。策略和凭据只在 `conf/backup.yml`，系统页面只负责展示结果。

所有命令都在**宿主机**执行（不是容器里），统一入口：

```bash
cd /home/liushangzhi/docker/biotech-plus/backup
./venv/bin/python backupctl.py <子命令> [参数]
```

## 1 前置检查（3 条）

```bash
docker ps --filter name=biotech-plus-mysql      # 容器在跑
command -v zstd                                 # 宿主机有 zstd（容器里没有）
./venv/bin/python backupctl.py check --config-only             # exit=0 说明 yml 能读
```

## 2 首次部署（4 步）

```bash
cd /home/liushangzhi/docker/biotech-plus/backup
cp conf/backup.yml.example conf/backup.yml && chmod 600 conf/backup.yml   # 1) 建配置
vi conf/backup.yml                                                        # 2) 填库名/口令/上报 token
./venv/bin/python backupctl.py db-full --type manual                                     # 3) 先手工跑通一次
./venv/bin/python backupctl.py install                                                   # 4) 生成 timer，按输出的命令 enable
```

第 4 步 `install` 只写文件、不启用，要再执行它打印的三条：

```bash
systemctl --user daemon-reload
systemctl --user enable --now backup-db-full.timer backup-db-binlog.timer backup-prune.timer backup-check.timer
loginctl enable-linger "$USER"        # 未登录也要跑
```

## 3 命令表

| 命令 | 作用 | 频率 | 失败码 |
| --- | --- | --- | --- |
| `db-full [--type manual] [--date YYYY-MM-DD]` | 全量：mysqldump → 宿主 zstd → md5 → OSS（可选）→ 上报 | 每周（yml `full.schedule`） | 4 |
| `db-binlog [--date YYYY-MM-DD]` | 增量：从上次终点拉到当前 binlog 位点 → 上报 | 每天（`binlog.schedule`） | 4 |
| `prune [--dry-run]` | 删本地过期全量/增量/日志 | 每周（`prune.schedule`） | 0 |
| `check [--config-only]` | 巡检：timer 漂移、binlog 保留余量、待补报 | 每天（`check.schedule`） | 3=有问题 |
| `install` | 按 yml 生成 `backup@.service` + 4 个 timer | 改 schedule 后 | 0 |
| `drill --date D` | 恢复到 D 日 02:10 归档点（=最近可用全量 + 后续 binlog 回放），灌进 `<库名>_drill`；`--check-only` 只出计划 | 每月手工 | 4 |

退出码：`0` 成功 / `2` 配置错（没做任何事） / `3` 巡检发现问题 / `4` 执行失败。

stdout 只有一行 `exit=N | summary`，明细看日志：

```bash
tail -20 log/backup.log                     # 每次运行一行
tail -30 log/db-full/$(date +%F).log        # 当次全量明细
tail -30 log/db-binlog/$(date +%F).log      # 当次增量明细
```

## 4 配置最少要改什么

| 场景 | 改哪 | 改完做什么 |
| --- | --- | --- |
| 不用 docker（宿主机有 mysql-client） | `mysql.use_docker: false`，`container` 可删，`host/port` 写宿主可达地址 | 跑 `check` 确认「客户端命令齐全」，再 `db-full --type manual` 试一次 |
| 恢复后要校验哪些表 | `drill.verify_tables: {ry-vue: [sample_file, analysis_report, product_config, project_config]}` | 下次 `db-full` 落快照后生效；`drill` 会逐表比对行数/最大主键 |
| 换库 / 加库 | `mysql.databases: [ry-vue, nkb]`（一组库一起备、一起恢复） | 直接跑；下次全量生效 |
| 排除日志表 | `mysql.exclude_tables: {ry-vue: ["sys_oper_log", "tmp_*"]}` | 跑一次全量，日志里确认 `排除规则未命中` 没出现 |
| 改时间 | `mysql.full.schedule` / `binlog.schedule` / `prune.schedule` / `check.schedule` | **必须** `install` + `daemon-reload`，否则跑旧时间 |
| 上报失败 | `report_api.token` 与后端 `api.token.tokens[0].value` 对齐，`client_id` 不能空 | 跑任一子命令会自动补报历史失败 |
| 上 OSS | `oss.enabled: true` + endpoint/bucket/AK | 跑一次全量，看日志 `oss=yes`、页面 OSS 路径有值 |

口令一律 `docker exec -e MYSQL_PWD=…` 传，别写进命令行历史。

## 5 日常看三处

1. `./venv/bin/python backupctl.py check`：`problems=0` 最好，WARN 逐条处理；
2. 页面「数据备份 → 数据库备份」binlog 页签：最近一条「链」= `接上` 或 `链起点`，不能是 `未接上`；
3. `ls state/pending-report/`：为空。有文件 = 上报失败（后端没起或 token/clientid 不对）；
4. `cat state/drill/<日期>.json`：最近一次恢复的 `result` 与 `verify_after_full.tables`，四张业务表都应 `PASS`。

产物与状态：

```text
/home/liushangzhi/backup/biotech-plus/db/full_<日期>.sql.zst      # 全量包
/home/liushangzhi/backup/biotech-plus/binlog/<日期>/mysql-bin.*    # 增量
backup/state/full-baseline.json                                    # 全量基线位点
backup/state/binlog-pos.json                                       # 增量起点（丢了会从最近全量重拉）
```

## 6 恢复

```bash
# 1) 先问「这个日期还能不能恢复」：只构建计划、校验实体，不 DROP、不恢复
./venv/bin/python backupctl.py drill --date 2026-10-29 --check-only

# 2) 真恢复：找到 <= 10-29 最近一份可用全量 + 后续 binlog，回放到 10-29 02:10 归档点
./venv/bin/python backupctl.py drill --date 2026-10-29

# 3) 精确到时刻（优先于 --date）
./venv/bin/python backupctl.py drill --to "2026-10-29 18:00:00"

# 4) 不带参数 = 恢复到最新可恢复点（最后一段归档的完成时刻）
./venv/bin/python backupctl.py drill
```

- 目标库 = `<生产库名><drill.database_suffix>`（默认 `_drill`），每次先 DROP 再灌，两次演练不叠加。
- 演练实例看 `drill.mysql`（host/port/user/password），与备份来源解耦；留空则回落到生产实例（同实例只换库名，脚本 WARN）。
- 恢复前先构建 Recovery Plan：full 与每个 binlog 文件按「本地 → OSS → 缺失」确认，缺一个就 FAIL，**不会先 DROP 再发现缺文件**。
- 灌完全量后、回放 binlog **之前**，按 `drill.verify_tables` 逐表比对「行数 + 最大主键」；差一张就 FAIL，结果写 `state/drill/<日期>.json`。
- 恢复到 D 日更晚的时刻要 D+1 的归档段（`--date` 默认只到 D 日 02:10；用 `--to` 指定更晚时刻时，缺那天归档就报「超出已归档窗口」）。
- 跨库名回放遇 DDL 会拒绝（`--rewrite-db` 会丢 DDL）：改用独立实例 + 空 suffix，或显式设 `allow_ddl_rewrite: true`。
- 覆盖现网恢复（停应用、DROP 生产库、灌包）见完整文档 §8 3，那条不走 drill。

## 7 故障速查

| 现象 | 处置 |
| --- | --- |
| `没有可用的起点` | 先 `db-full`，再 `db-binlog` |
| `binlog 文件不在服务端列表里` | 起点已被 MySQL 清理（`expire_logs_days=7`）⇒ 只能从新全量重做链 |
| 页面「未接上」 | 漏跑了某天；补跑只能从当前终点继续，历史那段要靠当时归档的 binlog 回放 |
| `上报失败，已落待补报` | 修好后端/token/clientid，跑任一子命令自动补报 |
| 上报 body `code=401` | 少了 `clientid` 头或 token 不匹配 |
| 上报 body `code=403` | `sys_backup` 缺 `backup:db:report` |
| `check` 报「漂移」/「timer 未安装」 | `install` + `systemctl --user daemon-reload` |
| `drill` FAIL（源库表数 > 演练库） | 全量包之后改过表 ⇒ 先 `db-full` 再 `drill` |
| `zstd: command not found` | 宿主机装 zstd（不要在容器里装） |

## 8 六个坑（先记住，能省一次事故）

1. **`--date` 不补历史**：db-binlog 的 `--date` 只改文件名和记录日期，增量起点永远是当前位点。要按日期找数据用 `drill --date`（它是恢复，不是补备份）。
2. **表数是基表口径**：`nkb` 66 张基表 + 51 个视图，页面显示 118 只看基表；核对要加 `TABLE_TYPE='BASE TABLE'`。
3. **`drill` 会写 binlog**：灌 118 张表进演练库，当天增量包会被撑大（实测几十 MB）；同实例演练排低峰，生产建议配独立 `drill.mysql`。
4. **`install` 不 enable**：timer 写好了不等于在跑，`systemctl --user list-timers | grep backup` 确认 NEXT 有时间。
5. **跨库名演练不重放 DDL**：`--rewrite-db` 只改 ROW 事件。含建表/改表的时间段会拒绝恢复；改用独立实例 + `database_suffix: ""`。
6. **`--date` 默认是当天 02:10，不是日终**：恢复点对齐每天 02:10 的归档定时。要恢复到当天 23:59:59 用 `--to "2026-10-29 23:59:59"`，并且需要 D+1 的归档段。
