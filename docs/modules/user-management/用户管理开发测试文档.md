# 系统管理 用户管理开发测试文档

用户管理负责建立药企人员账号、维护账号状态及分配角色。开发重点是让用户归属、角色授权和账号生命周期在页面与直接接口请求中保持一致，并补齐导入失败后的可追踪结果。

本文件供需求评审、开发实施和测试验收使用。请先确认第 4 节的开发任务及第 7 节的业务决策，再按用例执行验收。当前代码存在对应模块，本次补充可实施的开发内容，不将代码存在等同于功能已验收。

## 2 当前实现与数据约束

当前页面已接入真实 /system/user 接口，支持筛选分页、新增编辑、状态切换、重置密码、删除和 Excel 导入导出。新增及编辑抽屉会读取可选角色；新增显示账号与密码，编辑不显示这两个输入项。平台超级管理员可选择药企，普通用户使用当前药企，编辑时药企不可在页面修改。

服务端查询受药企隔离约束，账号、手机号、邮箱重复检查跨药企进行；删除为逻辑删除并清理用户角色关系。userId=1 受保护，批量删除包含当前登录用户会被拒绝。页面中隐藏操作按钮不代替服务端检查。角色信息与菜单权限涉及登录态，当前用户编辑、密码重置和状态修改路径未见统一会话失效处理，需专项补齐。

### 2 1 主要字段

| 字段 | 当前约束与开发关注点 |
| --- | --- |
| userId / tenantId | ID 为身份标识；tenantId 在 Bo 中必填。服务端校验药企存在、启用及归属；编辑不允许迁移药企。 |
| userName / nickName | 账号服务端 2–30 字符、必填并校验 XSS；昵称必填、最多 30 字符。页面账号仅必填，需对齐。 |
| email / phonenumber | 邮箱格式及最多 50 字符已校验；手机号 Bo 缺少格式约束，前端存在手机号正则。非空值做全局重复检查。 |
| password | 新增与重置控制器使用 BCrypt；普通编辑 Bo 仍包含 password 字段，应使用字段白名单防止绕过专用入口。 |
| sex / status | 页面使用字典，状态 0 正常、1 停用；直接请求缺少统一枚举校验。 |
| roleIds | 页面要求至少一个角色；服务端 @Size(min=1) 不拒绝 null，关系写入辅助方法遇空集合提前返回。 |
| delFlag / remark | 用户采用逻辑删除；备注与业务长度约束需与数据库及页面共同核对。 |

## 4 开发内容与实施顺序

以下任务均为计划开发、待评审，尚未修改业务代码。P0 优先处理权限、数据正确性和事务问题；P1 补齐交互与异常。按任务顺序实施，接口或数据库方案评审通过后再编码。路径别名见第 8 节。

### DEV USR 001 统一输入校验与更新白名单

优先级 P0；关联 REQ-USR-003、REQ-USR-004、REQ-USR-005。

现状依据：B/java/org/dromara/system/domain/bo/SysUserBo.java 的密码与状态缺少专用约束；SysUserController 的 resetPwd、changeStatus 未对完整 Bo 使用分组校验。普通 updateUser 仍接收含 password 的对象。

开发方案：在现有 Bo 或新增专用请求对象中区分新增、编辑、状态、重置校验；新增必须提供密码，重置必须提供目标 ID 和合规密码。普通编辑显式排除 password、delFlag 等非资料字段。统一账号、昵称、手机、邮箱边界；同步 F/views/system/user/modules/user-operate-drawer.vue 和 user-password-drawer.vue。沿用加密及 BCrypt，不新增明文存储。

完成标准：直接提交空密码、非法状态、超长昵称和编辑夹带 password 均被拒绝或明确忽略白名单外字段；正常编辑保持原密码可用。覆盖 TC-USR-005 至 010，失败无部分数据更新。

### DEV USR 002 收紧角色分配与药企边界

优先级 P0；关联 REQ-USR-002、REQ-USR-008。

现状依据：SysUserServiceImpl.insertUserRole 对 null 或空角色集合提前返回；Bo 的 @Size 不能拦截 null。角色存在性检查与保留角色过滤已有实现，但仍需明确停用及可委派范围。

开发方案：新增及授权入口显式要求非空角色；是否允许无角色账号先按第 7 节评审。对角色 ID 去重并校验存在、状态及操作者可分配范围；统一普通编辑与 authRole 的服务层校验。修正 F/service/api/system/user.ts 中 authRole 的参数绑定，使其与控制器一致。归属校验保留在服务层，批量操作先校验全部目标。

完成标准：null、空、重复、不存在、停用及保留角色分别有稳定结果；伪造药企和跨药企 ID 拒绝。新增失败不留下用户孤立记录，TC-USR-003、004、015、016 覆盖。

### DEV USR 003 统一账号变更后的会话处理

优先级 P0；关联 REQ-USR-006、REQ-USR-007。

现状依据：SysUserServiceImpl 的 updateUserStatus、resetUserPwd、updateUser 等路径未见统一注销旧会话调用；角色模块已有 cleanOnlineUser 的处理，可评估复用。

开发方案：提取共享账号权限变更处理，事务提交后清除受影响用户全部有效会话或使权限版本失效。建议停用、删除及重置密码立即失效，启用不恢复旧会话；角色变更要求重新认证或可靠刷新权限。前端明确提示影响范围，异常记录可追踪。该行为细节待评审。

完成标准：用两个浏览器会话和直接 API 验证旧令牌不能继续调用已收回权限；不只检查登录页面。会话失效失败有记录并可重试，TC-USR-011 至 014 覆盖。

### DEV USR 004 完善导入结果与错误展示

优先级 P0；关联 REQ-USR-008、REQ-USR-009。

现状依据：B/java/org/dromara/system/listener/SysUserImportListener.java 逐行调用服务，累积失败后抛异常，可能已保存部分成功行；模板没有 roleIds。user-import-modal.vue 使用 HTML 展示返回消息，失败后可能不刷新列表。

开发方案：优先保留逐行导入，返回可追踪的成功、失败及原因，不伪称整批回滚；如业务选择全量事务须另评估文件规模。评审默认角色来源，禁止静默生成无角色账号。服务端校验文件及每行归属；前端以纯文本或受控结构展示错误，不直接插入包含输入数据的 HTML；只要存在成功行就刷新。限制与提示须前后端一致。

完成标准：一好一坏两行、覆盖开关、跨药企账号及恶意 HTML 文本均有准确结果，无未授权写入或脚本执行。TC-USR-017、018 记录每行证据与角色关系。

### DEV USR 005 补齐列表和表单交互

优先级 P1；关联 REQ-USR-001、REQ-USR-010、REQ-USR-011。

现状依据：F/views/system/user/index.vue 的状态控件未显式按 edit 权限限制；超级管理员行操作隐藏但选择列仍可选。多个抽屉提交未见统一保存锁。

开发方案：状态按钮按权限禁用并在失败后恢复真实值；受保护行禁止勾选；保存、重置和导入处理中防止重复操作，finally 释放状态。按平台使用需要评审药企筛选项，普通用户不提供跨药企选择。用户名长度与动态密码必填规则和后端保持一致；导出复用当前查询条件。

完成标准：无 edit 权限仅可查看；连续点击只产生一次有效写入；失败保留输入并可重试，筛选及导出结果一致。TC-USR-001、002、019 至 022 覆盖。

### DEV USR 006 确定唯一性与审计策略

优先级 P1；关联 REQ-USR-003、REQ-USR-012。

现状依据：账号全局唯一数据库索引与逻辑删除并存；应用重复检查可能排除已删除记录。手机号和邮箱的应用层检查还需验证并发行为。

开发方案：建议账号一经使用不复用，以保留审计可追踪性；应用查询应包含已删除账号并返回明确占用提示。若选择允许复用，须另写迁移及历史关联方案。手机号、邮箱的空值语义和删除后复用另评审，再决定是否加索引。并发唯一冲突转为业务错误，操作日志对密码字段脱敏。

完成标准：并发同账号最多一条有效记录；删除后重建按已确认策略提示；日志含目标与结果，无凭据。TC-USR-023、024 覆盖，数据库变更另交迁移及回滚。

### 4 7 数据变更与联调要求

先沿用现有表和逻辑删除约定，不直接改初始化 SQL 充当已部署环境升级。若任务确需新增索引或字段，在 script/sql/update 下新增经评审的增量迁移；先检查存量异常，给出兼容及回滚方案。简单查询使用 MyBatis-Plus，复杂多表查询按项目约定放 Mapper XML。

每次改动同步前端 API 类型、参数绑定、服务端校验与测试。涉及数据库关系的写入在同一事务中完成；会话失效和缓存处理属于事务外效果，应在提交后执行并记录失败，不以数据库回滚假装撤销已失效的会话。

联调顺序：先补用户身份与药企归属校验，再处理角色及用户关系，最后联调菜单授权、路由与按钮权限。用户管理中的角色选择可先使用隔离环境预置角色，最终必须执行三模块联动验收。

每例前置角色须具有接口所需权限；权限不足用例除外。涉及“直接请求”的用例使用隔离环境已有接口测试工具，保留脱敏请求、响应、前后数据及操作日志。建议目标尚未开发时记录为“未实现”或“失败并关联缺陷”，不得调整预期以掩盖差异。

## 7 待确认事项与实现差异

1. 密码规则：建议统一为现有前端 6–18 位及混合字符校验，再由业务确定是否强化；不能仅依赖前端，默认重置密码不得写入文档。

2. 无角色账号：建议普通新增必须有角色；导入需明确默认角色或增加受控映射，不应静默产生无法正常使用的账号。

3. 会话生效：建议停用、删除、重置密码立即使旧会话失效，角色变更重新认证；需确认用户提示及并发影响。

4. 导入部分成功：当前可能逐行落库后返回失败。建议保留逐行模式并给出准确报告；若选择整批原子性，开发及测试需同步调整。

5. 账号名建议永久不复用；手机号、邮箱删除后能否复用以及普通管理员可委派哪些角色，仍需评审。

权限与菜单批量删除方向已由用户确认；本节补强细节仍为待评审。评审后保留既有需求及用例编号，调整规则、开发任务和预期结果，避免测试按不同版本验收。
