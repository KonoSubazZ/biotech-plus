# 质控管理 湿实验质控开发测试文档

湿实验质控用于维护样本实验阶段的质控原始记录、人工状态及后续判定依据。本稿供湿实验、运营、开发与测试人员评审，重点补齐类别隔离、实验失败追踪和样本指标导入，保留重测与修订历史。

面向需求评审、开发拆分与测试验收。当前记录维护已经存在；自动判定、完整证据链及业务闭环未在本模块落地。本稿把当前实现与建议开发分开，不能将静态代码核对视为业务测试通过。

### 2 3 开发边界与目标流程

记录来源 → 确认药企、样本及 wet_lab 类别 → 校验原始结果 → 保存 pending → 匹配本类别标准并生成独立判定 → 有权人员确认 → 保留历史版本及下游引用。当前仅记录 CRUD 和人工状态字段存在，其余步骤为待评审开发目标。

湿实验失败目标分支：固化失败环节、失败编码和原始证据 → 按实验室或病理责任角色补原因 → 依已评审签署流程签署 → 运营审核、交付及归档。架构图给出上述业务方向，当前模块没有失败说明、签名回调或审核状态机；不得仅将人工状态改成 failed 就宣称流程完成。

样本关联是前置依赖：QcRecord 的 subbarcode 与现有 SampleInfo.barcode 是否等价尚待确认；录单产品 erpTestName、sampleProductCode 到产品配置的映射也需验证。不得使用不存在的 sample_file.subbarcode/product_name 字段写 SQL，不能按同名产品跨药企猜测。优先通过稳定 ID 建立可追溯关系。

判定建议先验证样本、产品及唯一启用标准，再严格解析结果并比较；缺关联或缺标准为 no_standard，存在有效标准但结果不可解析为 non_numeric，闭区间内 passed、外 failed。单位冲突、多候选、非法阈值另给明确不可判定原因，具体返回枚举待评审。只有原始结果可保留 <0.5 等文本，标准阈值仍遵守质控标准文档的纯数值目标；不得对表达式作部分数字解析。

## 4 开发任务与实施顺序

以下任务均为“待评审、未开发”。P0 完成隔离、有效性和记录保护；P1 完成判定与交互，判定依赖样本关联和标准契约；P2 完成导入、失败证据及跨模块闭环。共享代码统一修改并回归两个菜单，不复制两套 Service。简称 Q=template-backend/ruoyi-modules/ruoyi-qc/src/main，F=template-frontend/src；具体文件列于第 8 节。

### DEV WET 001 补齐药企归属和类别授权

优先级 P0；关联 REQ-WET-002、REQ-WET-003、REQ-WET-013。

现状依据：QcRecord 继承 BaseEntity，Bo/实体/Vo 未声明 tenantId；表有 tenant_id 默认值。租户拦截器对超管跳过过滤。两个菜单共享相同权限字符串，Service 列表只在收到 qcCategory 时过滤，详情和删除没有类别规则。

开发内容：在 Q 的 QcRecordController、QcRecordServiceImpl、domain/bo/vo 补充可信目标药企与类别授权。普通用户归属来自上下文，超管显式选药企；读写记录时逐项检查。评审采用独立类别权限或服务端授权类别集合，具体权限名待定；不得仅将 role 名或客户端参数当授权依据。未传类别只能返回已授权集合，非法值拒绝，编辑不能将 wet_lab 静默改成 bioinfo。前端继续复用 QcRecordPage，新增明确归属提示。

完成标准：同药企不同类别和不同药企分别覆盖列表、详情、增改删；超管新增不落默认药企。混合非法批次全部拒绝。

### DEV WET 002 修复字段校验和录入规则

优先级 P0；关联 REQ-WET-004、REQ-WET-005。

现状依据：QcRecordBo 的 NotBlank/Size 在默认组，Controller 分别校验 AddGroup/EditGroup，分组未继承 Default。Service 新增直接映射插入，更新只检查 ID 存在；前端仅校验条码、项目、状态必填。

开发内容：显式设置新增编辑的校验组，服务端限制状态和类别枚举；条码 80、项目 100、结果 50、操作员 80、备注 500 字符。统一首尾空白处理；结果保留原文，不把 <0.5 或 20% 强转数字。检测时间约定时区和格式，拒绝非法日期；operator 作为来源文本与登录操作者分开。清空可选字段采用显式更新语义。真实重复实验允许多次记录，重复请求另设幂等依据，不能直接加“条码+项目唯一”。

完成标准：绕过页面提交也受约束；合法空结果和数值 0 不混淆；清空后回查无旧值，时间跨日显示一致。

### DEV WET 003 建立人工确认与修订规则

优先级 P0；关联 REQ-WET-006、REQ-WET-007。

现状依据：人工状态目前就是通用编辑表单中的 NSelect，新增也能选择 passed/failed；无专用确认权限或状态迁移检查。operator 是自由文本，日志注解仅说明 CRUD 留痕，不能当作电子签名或完整变更历史。

开发内容：建议普通新增固定 pending，确认单独校验权限和状态，记录确认者、时间及原因；是否要求复核人不同于录入人由业务评审。已确认记录修改走修订，保留旧结果、标准快照和关联；结果变动后的新版本回 pending，禁止无感保留旧确认。补乐观并发检查或等效机制，确认与修改竞争由事务拒绝过期操作。新增确认、版本字段及接口均为拟定契约，评审后确定名称及迁移。

完成标准：直接请求绕过确认仍拒绝；修改结果不会沿用过期人工结论；旧版本、理由和真实操作者可追溯。

### DEV WET 004 实现样本关联和独立自动判定

优先级 P1；关联 REQ-WET-008、REQ-WET-009。

现状依据：QcRecordServiceImpl 只有单表 CRUD；Vo、前端类型和列表均无 judgeResult。Mapper XML 为空占位。历史设计依赖 sample_file.subbarcode/product_name，现有 SampleInfo 提供 barcode、erpTestName、sampleProductCode，不能照抄旧关联 SQL。

开发内容：先与录单、产品配置确认 subbarcode 对 barcode 的映射及重复条码处理，优先保存可信样本/产品 ID；样本产品编码仅为待验证候选，禁止猜测名称或跨药企匹配。复杂关联放 Q/resources/mapper/qc/QcRecordMapper.xml。按 wet_lab 及启用产品、标准匹配，BigDecimal 严格解析，采用已评审闭区间和单位规则。拟新增独立判定结果、原因、标准 ID/阈值/单位/版本快照；现有 status 不复用。界面新增判定列和筛选，接口/类型同步。筛选应全量正确计算 total，不能复制旧 5,000 条截断方案。

完成标准：数值 10–20 的软件测试中 10、20 通过，9.99、20.01 失败；分类及药企不串标准。标准修订不重算已确认历史；超过 5,000 条仍分页完整。

### DEV WET 005 补齐湿实验失败处理契约

优先级 P2；关联 REQ-WET-010。

现状依据：架构图区分实验室员工和病理医师责任分支，再进入电子签署与运营审核。qc_record 当前只有通用结果、状态和备注，缺失败环节、责任分工和证据模型。

开发内容：先定义失败记录与质控记录、实验批次的稳定关联，明确失败编码字典、责任选择、原因必填和证据引用。未明确责任或原因不得进入目标签署状态。实验失败说明采用受控版本；签署与运营审核为跨模块依赖，签署失败保留可重试状态，回调按已确认服务契约鉴权并幂等。外部上上签仅为架构意图，本次不确定供应商参数、不实现自动发送。

完成标准：失败环节、责任角色、原因、证据、签署与审核状态可逐项追溯；任一前置缺失不能宣称已签署或已归档。重测保留原失败记录。

### DEV WET 006 设计湿实验导入和重测追溯

优先级 P2；关联 REQ-WET-011、REQ-WET-012。

现状依据：本菜单没有导入按钮和 Controller 接口。历史 spec.md 提到 sample_qc_info 的 30+ 指标，字段未穷举；旧导入依 sample_date+sample_code，与现有 SampleInfo 字段和关系未核准。

开发内容：先决定首期导入对象是逐项目质控记录，还是独立样本详细指标，分别给出完整模板、类型、单位、必填和版本；不能把旧 30+ 指标挤入 qcResult/remark。基于已确认样本键在同药企匹配，限定 wet_lab；未知或多匹配逐行报告。解析前校验文件格式、大小、表头、行数与公式策略，沿用 ruoyi-common-excel；阈值待评审。建议有效行可导入、错误行报告，系统异常事务回滚；返回总行数、新增、跳过、失败及行号原因。定义来源记录键和文件摘要幂等，重测产生新记录，已确认结果不自动覆盖。证据走现有存储能力并检查访问权限。

完成标准：模板无遗漏列和静默首行丢失；错误行可定位，重放不重复，真实重测可区分；无跨药企匹配和已确认结果无痕覆盖。

### DEV WET 007 落实引用保护和审计留存

优先级 P0 与 P2 分阶段；关联 REQ-WET-007、REQ-WET-013。

现状依据：deleteByIds 只拒绝空集合，随后逻辑删除并返回 TRUE，不校验实际影响数、确认状态或下游引用。DDL 没有样本外键或业务唯一键；现有通用日志不等于结果版本、原始证据或报告引用模型。

开发内容：P0 校验整批记录存在、药企、类别和可删除状态，任一无权、未知或已确认项整批失败；未确认且无引用的自建记录才允许逻辑删除。P2 与报告、失败说明和签署模块建立真实引用契约；没有引用模型时应记录依赖，不能虚构表查询。用同一事务或并发控制避免确认/下游引用与删除竞态。保留结果前后值、操作者和原因，源文件仅记录可授权访问的引用与摘要。

5. 导出、自动推送消息以及生产电子签名服务不在本次默认实现范围。P2 先评审提供方、接口、失败恢复及权限；本稿不替代业务验收或授权生产写入。
