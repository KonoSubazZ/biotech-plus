# 文档结构与证据要求

面向需求提出者、开发者与测试者。按模块复杂度展开，不把一个小功能强行写成大型生产规范。

## 建议结构

1. **概览与范围**：目的、角色、边界、版本、日期、实现基线、评审状态。开头说明读者要核对什么。
2. **需求与验收标准**：稳定编号、具体规则、可观察结果、来源类别。口述变更使用“原规则 → 新规则 → 影响范围”记录。
3. **开发说明**：页面交互、接口、字段、数据约束、核心流程、权限及异常。准确引用项目路径；开发前用规划说明，开发后用当前实现说明。
4. **测试准备**：隔离环境、角色与数据、依赖服务、清理策略。账号用角色或占位符；测试数据明确为测试数据。
5. **测试用例**：编号、优先级、关联需求、前置条件、操作和预期。长步骤写段落；状态放执行记录，避免难读的超宽表。
6. **执行与验收记录**：命令、日期、环境、版本、执行者、实际结果、证据。未执行时留“待执行”，不能填写“通过”。
7. **待确认与实现差异**：问题、影响、建议及决定状态；来源冲突有单独记录。
8. **依据与变更记录**：代码或资料路径、必要时符号名/真实行号；记录本次文档改动。

字段、接口、角色矩阵适合表格；叙述、流程和完整测试步骤适合正文。仅在需要跨页对照时使用重复表头，不做装饰性封面。

## 需求示例

`REQ-TEN-001`：平台超级管理员可以维护租户；普通用户不能通过页面或直接请求访问租户管理操作。验收必须检查服务端拒绝，不能仅检查按钮隐藏。依据若仅为代码，则标为“当前实现 待业务确认”。

## 用例示例

用例编号 `TC-TEN-001`，关联 `REQ-TEN-001`，优先级 P0。

- 前置：隔离环境中有普通用户 A，其所属租户启用。
- 操作：A 登录后直接请求管理列表及新增接口。
- 预期：业务请求被拒绝；没有返回其他租户目录，也没有新增记录。不预设未查证的 HTTP 状态码。
- 执行记录：待执行。只有实际执行并保存证据后才能更新状态。

## 证据与一致性检查

- 文档开头记录读取时的 Git 提交，工作区有相关未提交改动时一并说明，不能把提交号当作整个工作区的精确版本。
- 每项需求至少关联一个测试用例；每个用例的需求编号必须存在。删除需求时保留废弃说明，避免编号漂移。
- 当前代码支持、建议实现与用户确认是独立状态。不能因为存在控制器、方法或旧测试就声称功能验收通过。
- 业务测试默认不执行。若用户授权运行，先检查脚本是否创建/修改数据库、发送消息或涉及真实服务，再按授权范围执行。
- 不把历史成功记录复制成本次结果；不推断测试用例全部覆盖、全部通过或可上线。
- 同次输出的 MD 与 DOCX 必须来自同一内容源；转换后检查标题、表格行数、用例编号和文本内容，最后逐页检查 Word 渲染效果。
